# Последовательный автономный запуск оркестраторов (две очереди A↔B)

Как мы гоняем два оркестратора **по очереди, автономно**, чтобы они не делили RAM/ресурсы и не дрались
(а шли во времени друг за другом). Два зеркальных паттерна — выбираешь по ситуации.

Реальные кейсы (2026-06-30, проекты PROJECTA `channel2_live` ↔ projectd projectc):
- **Паттерн 1:** ждали финала PROJECTA → запускали projectd-волну (T99/HEADER/CRYPTO).
- **Паттерн 2:** прогнали projectd-волну (T102/T103/T104) → сняли PROJECTA с паузы.

---

## Кирпичики (в `/work/settings/`)

| Файл | Что делает |
|------|------------|
| `wave_launcher.template.sh` | Лончер одного агента: `claude -p < TASK_FILE`, PID в `PID_FILE`. Промпт через stdin (без двойного eval). Конфиг через env: `PROJECT_DIR TASK_FILE PID_FILE LOG`. |
| `wave_supervisor.template.sh` | **RL-aware супервизор** одного таска (env-параметризован: `TASK PROJ_DIR TASK_FILE PID_FILE LOG REPORT JSONL_DIR`). Респавн по death/stall; **5-часовой/session-лимит сам пережидает циклом** (см. HOW_TO_RUN §9.3bis); выход по строке `STATUS:` в отчёте. |
| `queue_wave_after_orchestrator.template.sh` | **Паттерн 1**: волна B ПОСЛЕ оркестратора A. |
| `queue_wave_then_resume_orchestrator.template.sh` | **Паттерн 2**: оркестратор A ПОСЛЕ волны B (resume A в конце). |

«Волна B» = список тасков, гонится **по одному агенту за раз** (один `wave_supervisor` в момент времени),
каждый под RL-aware супервизором, со скрин-проверкой и дебаг-циклом (это в самих таск-файлах).

---

## Паттерн 1 — «B после A» (`queue_wave_after_orchestrator.template.sh`)

Сторож сидит и ждёт, пока **оркестратор A закончит**, затем запускает волну B.

Логика:
1. **Финал A = смерть его supervisor-сессии(й)** — `tmux ls | grep -E "$A_SUP_RE"` пуст. НЕ по progress.md (агент мог не дописать) и НЕ по pid (бывает stale).
2. **Хвосты A**: detached-агент мог пережить супервизор → ждём с cap'ом (pid-файл агента A + живой `claude(agentuser)` с cwd под проектом A).
3. **RAM-гейт** (`MemAvailable ≥ RAM_MIN_KB`) + осесть.
4. **Последовательный прогон B**: на каждый таск — свой `wave_supervisor` в своей tmux-сессии; ждём её смерти (супервизор сам выйдет по отчёту/лимиту respawn); читаем `STATUS:`; TG-пинг; следующий. Идемпотентно (если отчёт со STATUS уже есть — пропуск).

Заполнить в НАСТРОЙКАХ: `A_SUP_RE` (regex сессий супервизора A), `A_PID_FILE`, `A_CWD_PREFIX`, `LOG`, массив `TASKS`.

Запуск:
```bash
# (заполни НАСТРОЙКИ в копии шаблона)
tmux new-session -d -s wave_qwait "bash /work/<PROJECT_B>/.../queue_after_A.sh"
sleep 3 && tail -3 <LOG>            # "armed"
# отмена до старта B: tmux kill-session -t =wave_qwait
```

## Паттерн 2 — «A после B» (`queue_wave_then_resume_orchestrator.template.sh`)

Сначала прогоняем волну B, **по окончании автономно возобновляем оркестратор A** (который стоял на паузе).

Логика:
1. **Последовательный прогон B** (как в Паттерне 1, п.4).
2. **RAM-гейт**, затем **resume A**: `tmux new-session -d -s $A_SESSION -c $A_CWD "$A_RESUME_CMD"`. Идемпотентно (если A уже жив — не дублируем). Resume-команда A обычно задокументирована в его `progress.md` (на паузе).

Заполнить: массив `TASKS`, `A_SESSION`, `A_RESUME_CMD`, `A_CWD`.

Запуск:
```bash
tmux new-session -d -s wave_qrun "bash /work/<PROJECT_B>/.../wave_then_resume_A.sh"
sleep 3 && tail -3 <LOG>
# отмена до старта следующего таска: tmux kill-session -t =wave_qrun
```

## Важные нюансы (грабли, которые уже наступали)

- **Сигнал финала — смерть SUPERVISOR-сессии (`..._sup`), не pid/progress И НЕ сессия самого оркестратора.** `tmux has-session -t "=<имя_sup>"` (точное `=`, не префикс).
  🔴 **Кейс PROJECTA↔FB10 (2026-07-03): сторож завис на 4.5 часа.** Сторож `queue_projectg_after_fb10.sh` ждал исчезновения сессий по regex `orv_fb10` (`{ tmux ls; runuser -u agentuser -- tmux ls; } | grep -qE 'orv_fb10'`). FB10 отработал (ALL_DONE 00:52, супервизор `orv_fb10_sup` САМ вышел — корректный сигнал финала), НО интерактивный **REPL оркестратора `orv_fb10` после ALL_DONE сам НЕ закрывается** (claude REPL, см. HOW_TO_RUN §9.9) — а regex `orv_fb10` префикс-матчил и мёртвый `orv_fb10_sup`, и ЖИВОЙ `orv_fb10` → `fb10_alive` вечно true → волна не стартовала, пока REPL не прибили вручную (`tmux kill-session -t =orv_fb10`). 4.5 ч простоя.
  **Правила, чтобы не повторить:**
  1. Финиш-сигнал = ТОЛЬКО супервизор-сессия. Паттерн ДОЛЖЕН содержать `_sup` (напр. `A_SUP_RE='_sup:'` или точный `-t =<имя>_sup`), НИКОГДА голый префикс оркестратора (`orv_fb10` матчит и `orv_fb10_sup`, и `orv_fb10`).
  2. Ещё надёжнее — sentinel `reports/ALL_DONE_<WAVE>` (пишется ровно при финале) как основной сигнал: «ALL_DONE есть» ИЛИ «супервизор-сессия исчезла». Он однозначен, не зависит от лингер-REPL.
  3. §8.8 в HOW_TO_RUN: `grep <prefix>` префикс-матчит `<prefix>` И `<prefix>_sup` разом — всегда анкорь паттерны (`=имя`, `имя:`, `_sup`), не голый префикс.
  4. При финале оркестратора его REPL надо ПРИБИТЬ (`tmux kill-session -t =<orch>`) — сам он не выйдет; если сторож ждёт его смерти как сигнал финала (ошибка) — зависнет навсегда.
- **Хвосты обязательны:** detached `claude -p` переживает супервизор; не дождавшись — запустишь B в параллель с A (драка за RAM/SOCKS/VNC).
- **По одному агенту за раз.** Последовательность = один `wave_supervisor` активен; следующий стартует только после смерти предыдущей сессии.
- **RAM-гейт между тасками** — не стартовать тяжёлый таск в нехватке памяти.
- **5-часовой/session-лимит** — пережидается в `wave_supervisor` (см. HOW_TO_RUN §9.3bis: `RL_RE` должен ловить и `session limit`/`resets 7:30pm`; ожидание циклом, а не один таймаут — иначе многочасовой сброс убьёт оркестратор, кейс PROJECTA 2026-06-30).
- **FAIL одного таска НЕ блокирует следующий** — пингуем статус, идём дальше (resume A в Паттерне 2 делаем в любом случае по окончании B).
- **JSONL_DIR** для stall-детекта = каталог сессий agentuser конкретного проекта: `/home/agentuser/.claude/projects/-work-<project>`.
- **Запуск — от root**, агенты — `setsid runuser -u agentuser` (внутри `wave_supervisor`).
- **🔴 Идемпотентность: прошлый отчёт со `STATUS:` молча БЛОКИРУЕТ повторный запуск таска.** И сторож
  (Паттерн 1/2), и `wave_supervisor` идемпотентны: если `report_<TAG>.md` уже существует и содержит строку
  `STATUS:` — таск считается сделанным → агент НЕ запускается (сторож пишет «пропуск»; супервизор делает
  `finish_on_report` и выходит без запуска). Это by-design «не делать дважды сделанное», но у него есть капкан.
  🔴 **Кейс ZFISCAL2 (2026-07-05): «оркестратор не запустился».** Сторож `queue_projectg_after_fb13` корректно
  дождался финала FB13, поднял канал к кассе, дошёл до прогона волны — и **пропустил ZFISCAL2**, потому что
  `report_ZFISCAL2.md` остался с ПРОШЛОГО прогона со `STATUS: PARTIAL`. Не сбой — идемпотентность.
  **Тонкость:** проверка НЕ различает SUCCESS и PARTIAL/BLOCKED/FAIL — ЛЮБОЙ `STATUS:` = «сделано». Но
  PARTIAL/BLOCKED/FAIL значит «надо ПРОДОЛЖИТЬ», а не «готово» → повторный прогон обязан их игнорировать.
  **Правило — чек-лист ПЕРЕД повторным прогоном / RESUME таска (до постановки в очередь и до запуска супервизора):**
  1. Заархивировать прошлый отчёт: `mv chat/report_<TAG>.md chat/report_<TAG>_runN.md` (НЕ удалять — там
     находки; новый агент прочитает архив; если таск-файл ссылался на `report_<TAG>.md` как на источник —
     поправь ссылку на архив).
  2. Вычистить stale-PID: `rm -f /tmp/*_<TAG>.pid` (PID от прошлого прогона врёт — «живой» мёртвый процесс).
  3. Убедиться, что нет живого `<TAG>_sup`, и что окружение/канал (RustDesk :99 и т.п.) реально подняты —
     `verify`, а не «поднимал час назад» (канал за час отваливается; кейс ZFISCAL2 — RustDesk был NOT_VERIFIED).
  Иначе и сторож, и супервизор молча пропустят таск и выйдут — со стороны выглядит как «оркестратор не запустился».
  (Если нужен принудительный повтор в коде: сносить `report_<TAG>.md` перед запуском, ИЛИ вести идемпотентность
  ТОЛЬКО по `STATUS: SUCCESS`, а PARTIAL/FAIL перезапускать — но тогда добавь отдельный cap от вечного
  перезапуска всегда-PARTIAL таска.)
- 🔴 **RAM/ресурс-гейт сторожа: логируй КАЖДЫЙ тик (и `ok=0`) и не держи вечно после подтверждённого финала соседа.**
  Кейс fb14↔PROJECTA 2026-07-06: финал соседа пойман верно, но «устойчивый» RAM-гейт (`SUSTAIN×POLL`) молчал при `ok=0` →
  ~50 мин выглядел мёртвым. Сигнал финала соседа — первичный; RAM-гейт после него — лёгкая видимая страховка, не тугой
  порог. Подробно + ещё две грабли (снимать сторож по tmux-сессии, а не `pkill -f <путь>` = self-KILL exit 144;
  не редактировать скрипт, крутящийся в detached-tmux, — перезапускай начисто) — HOW_TO_RUN §12.4 / §8.5.

(`queue_after_projecta.sh`, `queue_projectd_then_resume_projecta.sh`, `wave_supervisor.sh`, `wave_launcher.sh`).

## Паттерн 1b — «A это ЦЕПОЧКА одноагентных волн» (нет единого оркестратора/`_sup`) → по УСТОЙЧИВОМУ ЗАТИХАНИЮ

Кейс PROJECTA VAT22 ← projectb (2026-07-13, сработало чисто в 01:09). Сосед A — НЕ один оркестратор с одним
`_sup`, а автономная эстафета из последовательных одноагентных волн (`sf_<task>_sup`, claude -p, cwd
`/work/projectb`), без единого драйвера/сентинела. Тогда «A закончил» ≠ «исчез его `_sup`»: между волнами A
его `_sup` тоже пропадает на паузу → канонный `while a_alive; do sleep; done` (Паттерн 1) выстрелит
ПРЕЖДЕВРЕМЕННО в зазоре между волнами A и подерётся с ним за ресурсы.

Сигнал финала для цепочки-A = УСТОЙЧИВОЕ ЗАТИХАНИЕ (не «первое исчезновение»):
- нет НИ ОДНОЙ `A_SUP_RE`-сессии И нет живого `claude(agentuser)` с cwd под `A_CWD` — **N ТИКОВ ПОДРЯД** (напр.
  6×90с = 9 мин), чтобы пережить паузы между волнами A. (RL-ожидание ВНУТРИ волны держит её `_sup` живым —
  это как раз защищает от ложного срабатывания в RL-паузе.)
- Перед стартом B ещё раз ПЕРЕПРОВЕРИТЬ затихание (в RAM-гейте): ожил A → сброс счётчика, назад в ожидание.
- Порядок безопасности: первый таск B — БЕЗВРЕДНЫЙ (у VAT22 — бэкап БД), опасный (правка данных) — гейтится
  успехом первого. Тогда даже ложный ранний старт не вредит.

🔴 Живучесть САМОГО сторожа (иначе эстафета молча не сработает — единая точка отказа):
- **HEARTBEAT: логируй КАЖДЫЙ тик** (видно, что жив и что видит: `sup=? agent=? clear=k/N`) + TG раз в ~1ч,
  пока ждёшь. Молчащий сторож не отличить «ждёт» от «умер» (§12.4, но здесь — про наблюдаемость самого
  сторожа, не только RAM-гейта: канонный главный цикл `while a_alive` молчит — добавь лог per-tick).
- **CRON-KEEPER** (`*/15`): если tmux сторожа умер (ребут/краш) и волна ещё не идёт и не сделана — поднять
  заново (идемпотентно: skip если есть ALL_DONE / жив B-супервизор / жив сторож).

Боевой комплект (с заполненными настройками): `/work/projecta/orch/vat/queue_vat22_after_projectb.sh`
+ `/work/projecta/orch/vat/vat22_qwait_keeper.sh` (cron).
