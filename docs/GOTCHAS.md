# Гочи claude-REPL framework (неочевидное)

Уроки, найденные при обкатке (2026-07-16). Держать рядом с шаблонами `claude_*.template.sh`.

## 1. claude НЕ работает от root
`claude --dangerously-skip-permissions` отказывается стартовать от root/sudo
(«cannot be used with root/sudo privileges for security reasons»). Поэтому агенты framework
запускаются ОТ пользователя **agentuser** (у него claude-auth в `/home/agentuser/.claude`).

Если задаче нужен root (например `/work/remote_tools/anydesk_projecta.sh`, где внутри `runuser -u agentuser`):
не запускай агента от root — сделай инструмент **user-aware**, чтобы он работал и от agentuser:
```bash
U(){ if [ "$(id -un)" = agentuser ]; then env DISPLAY="$DISP" "$@";
     else runuser -u agentuser -- env -i HOME=/home/agentuser PATH=... DISPLAY="$DISP" "$@"; fi; }
```
Дисплей `:99` принадлежит agentuser → agentuser обращается к нему напрямую, без `runuser`.
Стек, требующий root (`up`/сервис AnyDesk), поднимает оператор заранее; агент от agentuser его не трогает.

## 2. churn оркестратора (исправлено)
При рестарте таска новый launcher первым делом делает `tmux kill-session` на REPL-сессии и
добивал REPL ещё не вставшего предыдущего запуска → бесконечные перезапуски, ни один REPL не
стабилизируется. Фикс в `claude_orchestrator.template.sh`:
- `START_GRACE` (по умолч. 90с) — минимальный интервал между стартами одного таска;
- идемпотентный `start_task` — живую сессию супервизора не пересоздаёт и не killает.
Ставь `START_GRACE` > (STARTUP_WAIT launcher'а + PID-wait супервизора).

## 3. кодировка jsonl-пути
claude кодирует путь проекта, заменяя ВСЕ не-alphanumeric символы (и `/`, И `_`) на `-`:
`/work/remote_tools` → `-work-vnc-rnd`. Для stall-детекта супервизора путь считается как
`sed 's#[^a-zA-Z0-9]#-#g'`, а не только по слэшам — иначе ложный «no jsonl» и лишний respawn.

## 5. петля рестартов из-за отчёта БЕЗ строки STATUS (исправлено 2026-07-19)
Кейс PROJECTA T10 (live-касса): агент доделал работу и написал отчёт, но ЗАБЫЛ финальную строку `STATUS:`.
Механизм петли двухслойный:
- супервизор на опросе видит файл отчёта → `finish_on_report` → статуса нет → `AMBIGUOUS` → `exit 3` (kill agent);
- оркестратор проверял «сделан?» ТОЛЬКО по наличию валидного `STATUS:` (его нет) и НЕ фиксировал AMBIGUOUS →
  поднимал супервизор для того же таска заново → новый агент → снова `exit 3` → и по кругу.
`MAX_RESPAWN` не спасал: это лимит ВНУТРИ одного супервизора, а цикл создавал оркестратор, обнуляя счётчик.
Для live/1С каждый новый агент повторял разрушающие действия (рестарт киоска, переоткрытие `.epf`) → шторм
рестартов развалил живую 1С-форму агента.
Фикс:
- супервизор: если файл отчёта уже существует — `finish_on_report` вызывается ВСЕГДА (не только при непустом
  статусе), поэтому STATUS-less отчёт даёт немедленный `exit 3` без запуска свежего агента поверх;
- оркестратор: «отчёт есть, но без STATUS» (или live/1С-таск умер без отчёта) → терминальный **карантин**
  (`state/<task>.ambiguous`, отметка `[?]` в progress, пинг), авто-рестарт СТОП; `all_done`/цикл запуска
  карантин пропускают;
- live/1С-таски (`No-Respawn: true` или Resource-Lock ∈ {node1c,1c,vnc_1c,live,prod,fiscal,ofd}) → `MAX_RESPAWN=0`
  и оркестратор их не рестартит после смерти. Правило: **live-мутирующий таск при не-успехе ВСТАЁТ и зовёт
  человека, а не перезапускается**.
Профилактика на стороне агента: последняя строка отчёта — ровно `STATUS: ...`; live-шаги делать идемпотентными.

## 4. запуск оркестратора — ОТ agentuser
Оркестратор/супервизор/launcher — всё под agentuser, чтобы tmux/jsonl/claude-auth принадлежали ему:

## 6. гонка сериализации при спайке тасков одного lock + надёжная цепочка `chain_tasks` (2026-07-22)
Наблюдение (PROJECTA, live-касса): при быстром создании НЕСКОЛЬКИХ активных `.md`-тасков с ОДНИМ `Resource-Lock`
(`node1c`) оркестратор запустил ВТОРОЙ таск, пока первый ещё работал → **два агента разом на одной кассе** (конфликт).
Корень: state-файлы работающего таска (`.lock`/`.session`) транзиентно пропали (после чего `lock_active`/`active_count`
сочли ресурс свободным), усугублено коллизией jsonl-трекинга супервизоров в одном проекте (оба супервизора смотрели
один jsonl). Т.е. сериализация lock+`MAX_PARALLEL` НЕ железобетонна при спайке добавления тасков.

Надёжный обход — **watcher-цепочка** `chain_tasks.template.sh`: все таски цепочки, КРОМЕ первого, держать `.md.staged`
(оркестратор `.staged` не видит); watcher активирует следующий (`.staged -> .md`) ТОЛЬКО когда предыдущий ПОЛНОСТЬЮ
завершён — **отчёт содержит `STATUS:` И tmux-сессия таска закрыта**. Тогда активен-и-запускаем в любой момент максимум
ОДИН таск цепочки → оркестратор физически не может стартовать два. Запуск (пример):
```bash
TASK_DIR=/work/<proj>/orch/live/tasks REPORT_DIR=/work/<proj>/orch/live/reports \
  CHAIN="T43_x T46_y T47_z" \
  tmux new-session -d -s <proj>_chain "bash /work/settings/claude/chain_tasks.template.sh"
```
Профилактика: НЕ спамить много активных `.md` одного lock разом; для строгого порядка A→B→C — цепочка (staged + watcher).
Живой пример-инстанс: `/work/projecta/orch/live/chain_t43_t46_t47.sh` (лог `logs/chain_t43_t46_t47.log`).

## 7. «промпт не долетел до REPL» → ноль jsonl → 40-мин FATAL/карантин (исправлено 2026-07-23)
Кейс PROJECTA T49 (дважды подряд): агент поднялся, но задача не поехала — в `state/<task>.ambiguous`, supervisor-лог
`NO-JSONL 2419s ≥ 2400 → kill+respawn` → `FATAL` (no-respawn). Корень — в СТАРОМ `claude_agent_launcher.template.sh`:
он делал фиксированный `sleep 12`, затем ВСЛЕПУЮ `paste-buffer` + `Enter` и **не проверял, что промпт принят**. Если
REPL за 12с не отрисовал поле ввода (нагрузка / холодный старт / RAM-давление), вставка и Enter терялись → агент сидел
пустой → **jsonl не появлялся**. Единственная страховка — `NO_JSONL_LIMIT` (= `STALL_LIMIT`, у PROJECTA 2400с = 40 мин), а
для live/1С (`No-Respawn`) это не ретрай, а сразу FATAL + карантин → мёртвый конвейер и ручной разбор.

Фикс — в лончере (там ретрай дёшев и безопасен): **опрос готовности + ранний PID + submit-verify с ретраями**:
1. Вместо фиксированного `sleep` — опрос `capture-pane`: ждать, пока REPL отрисует поле ввода. Быстрый positive-маркер
   `READY_RE` (ASCII-футер claude: `Bypassing Permissions`, `for shortcuts`, …) + fallback-стабилизация (2 одинаковых
   непустых кадра) + потолок `READY_MAX` (30с). Trust-диалог принимается Enter, если всплыл.
2. PID пишется РАНО (сразу после `new-session`, до фазы готовности/submit), чтобы супервизор не счёл «launch failed»,
   пока идёт bring-up.
3. После вставки — **проверка старта агента по свежему jsonl** (тот же сигнал, что stall-детект супервизора; каталог
   `JSONL_DIR` теперь передаётся супервизором в лончер). Нет jsonl → **пере-submit** до `SUBMIT_TRIES` (4) раз. Пере-вставка
   в тот же REPL безопасна: без jsonl агент ещё ничего не сделал. Потерянная вставка → само-лечение <1 мин, а не 40-мин смерть.
Ключевое: корректность НЕ зависит от детекта готовности — даже при таймауте READY_MAX идёт submit+verify+retry, т.е.
худший случай = старое поведение ПЛЮС верификация. Проверено: happy-path (jsonl→«prompt accepted»), never-start (цикл
ограничен `SUBMIT_TRIES`, не виснет). Бэкап старых шаблонов: `_backup_launchfix_20260723_111453/`.
Тюнинг env лончера: `READY_MIN READY_MAX READY_RE SUBMIT_TRIES SUBMIT_VERIFY JSONL_DIR` (дефолты безопасны).

## 8. таск-ВЫВОД вместо таск-ГИПОТЕЗЫ → агент «чинит» несуществующий баг (PROJECTA T60, 2026-07-23)
Кейс: расследование «агентный codes/check расходится с прямым ГИС МТ». В таск был ЗАШИТ вывод как ФАКТ — заголовок
«найти и **починить** искажение», раздел «ДОКАЗАННОЕ РАСХОЖДЕНИЕ» («врёт НАШ агент»), заранее расписанная Фаза-фикс,
которая ПРЯМО велела «пересмотреть `ВердиктCodesCheck`». Фаза 1 (гейт) фактически показала ПОЛНОЕ совпадение полей на
идентичном входе — бага НЕТ (раннее расхождение было артефактом ручного теста: код декодировали с фото → усечённый
вход → `errorCode=7`). Но агент по инерции таска всё равно полез в правку `ВердиктCodesCheck` («verdict-neutral accuracy
fix»), рационализировав зашитую установку. Спасло только вклинивание в живой REPL (STEER_AGENT.md) со стоп-рулём +
`Escape` (агент откатил правку из своего pre-edit бэкапа, SHA==pre-edit; `.epf` не пересобирался).

Корень — НЕ агент, а **формулировка таска**: когда в тексте задачи стоит готовый вывод и заранее прописан фикс, агент
СКЛОНЕН его ПОДТВЕРЖДАТЬ и исполнять, а не ОПРОВЕРГАТЬ (confirmation drift; усиливается pre-scripted фазой-фиPROJECTAм).
«Гейт» в названии фазы этого не перебивает — перебивает только явный запрет.

Профилактика (писать таски так):
- Спорную причину формулировать как **ГИПОТЕЗУ для проверки**, а не как «ДОКАЗАННЫЙ факт». Дать и контр-гипотезу
  («расхождение может быть артефактом теста / состояние изменилось / чинить нечего»).
- **Фазу-фикс делать строго условной:** «Фазы фикса выполнять ТОЛЬКО ЕСЛИ гейт проверки провалился на ИДЕНТИЧНОМ входе».
- Явный выход-СТОП: «нет расхождения → закрыть `STATUS: SUCCESS` с выводом ‘бага нет’, код НЕ трогать, не пересобирать,
  не деплоить». Без этой строки агент дописывает «улучшение».
- A/B/сравнения гонять на **байт-в-байт одинаковом входе** (иначе разошедшиеся входы дают ложный «баг»).
Живой рычаг, если агент уже поехал в ложный фикс: STEER_AGENT.md (стоп-руль в REPL) + `Escape` для немедленного прерывания
текущего хода (очередь иначе подхватится только МЕЖДУ ходами — агент успеет доправить/задеплоить).

## 9. 🔴 `pgrep -fc … || echo 0` даёт "0\n0" — ожидатель слота НИКОГДА не стартует (08.08.2026)

Стоило пяти часов простоя цепочки лояльности при полностью свободной машине.

```bash
run=$(pgrep -u agentuser -fc "$EXECUTOR_PAT" 2>/dev/null || echo 0)   # 🔴 ТАК НЕЛЬЗЯ
```

`pgrep -c` при нуле совпадений печатает `0` **и возвращает код 1**. Срабатывает `|| echo 0`, и в
переменной оказывается двустрочное `"0\n0"`. Дальше `[ "$run" -lt "$MAX_EXECUTORS" ]` падает с
«integer expression expected», условие «слот свободен» **не выполняется никогда**, и ожидатель
уходит на второй круг — при живом исполнителе и при мёртвом одинаково.

Почему это так долго не замечали: умолчание `FORCE_AFTER_DEADLINE=1` маскировало дефект — очередь
всё равно стартовала по дедлайну, просто «почему-то не сразу». Дефект вылез, когда ожидатель
запустили с `FORCE_AFTER_DEADLINE=0` (осознанно: безусловный старт поднял бы второго исполнителя
на том же `Resource-Lock`). Тогда он честно прождал 420 минут и вышел ни с чем, а `progress.md`
показывал `T210 STATUS=SUCCESS` ещё в 13:08.

**Как правильно** (`wc -l` всегда даёт одно число и код 0):

```bash
run=$(pgrep -u agentuser -f "$EXECUTOR_PAT" 2>/dev/null | wc -l | tr -d " ")
```

Исправлено в `claude/wait_slot_and_launch.template.sh` и
`claude/wait_conditions_and_launch.template.sh`.

🔴 **Урок шире одной команды:** проба, которая ошибается в сторону «условие не выполнено», в
ожидателе неотличима от «ещё не пора» — она не падает и не пингует, а тихо ждёт. Любая новая проба
в ожидателях обязана быть проверена на ВЫРОЖДЕННОМ входе (ноль процессов, пустой вывод,
недоступный ресурс), а не только на рабочем. Ср. правило 1 в шапке шаблона: невозможность
проверить ≠ «условие не выполнено».

## 10. 🔴 Очередь со своим списком `TASKS` после его исчерпания идлит вечно (08.08.2026)

Оркестратор, поднятый с `TASKS='T210'`, отработал задачу и остался в `queue drained — idle,
watching tasks/ for new files`. Новые файлы `T*.md` он при заданном `TASKS` НЕ берёт: список
фиксирован на старте. Со стороны это выглядит как живая работающая очередь — сессия есть, лог
тикает, — поэтому вотчдог, который считает «сессия жива, значит всё в порядке», будет ждать
бесконечно.

**Практика для вотчдогов:** «сессия оркестратора жива» — НЕ признак того, что работа идёт.
Признак — живой исполнитель либо непустой список незакрытых задач, которые эта очередь реально
взяла. Если исполнителя нет N тиков подряд, а незакрытые задачи есть — поднимать очередь заново
на них, а не ждать. Образец — `/work/projecta/orch/loyalty/loyalty_watchdog.sh`.

## 11. 🔴 Тот же счётчик слота, второй перекос: `pgrep` считает исполнителем САМ оркестратор (09.08.2026)

Продолжение #9 и, по сути, его недолеченная половина. 08.08 убрали `|| echo 0`, поставили
`pgrep -u agentuser -f "$EXECUTOR_PAT" | wc -l` — и симптом «ожидатель не стартует никогда» остался,
потому что перекос был не только в коде возврата.

**Замер 09.08 (две реальные задачи в работе, T216 и T301):**

```
pgrep -u agentuser -f "claude --dangerously" | wc -l   → 4
реальных исполнителей                             → 2
```

Лишние двое:
1. **сам процесс-оркестратор** — он тоже `claude --dangerously-skip-permissions`, и `pgrep` его
   честно находит. Это постоянная добавка +1: при `MAX_EXECUTORS=2` и ОДНОМ живом исполнителе
   счётчик даёт 2, условие `2 < 2` ложно, слот «занят» навсегда;
2. **собственная командная строка пробы**, если счёт зовут не из файла-скрипта, а инлайном
   (`bash -c '… pgrep -f "claude --dangerously" …'`): шаблон лежит в argv измеряющего процесса,
   и `pgrep -f` матчит сам себя. В файле-скрипте этого не происходит — шаблон в теле файла, не в argv.

**Как правильно** — вычитать собственную цепочку предков (в ней и запустивший claude-оркестратор):

```bash
self_chain(){ local p=$$; while [ "$p" -gt 1 ]; do echo "$p"
  p=$(awk '/^PPid:/{print $2}' /proc/$p/status 2>/dev/null); [ -n "$p" ] || break; done; }
count_executors(){ local excl; excl=$(printf '%s\n' $(self_chain) $EXCLUDE_PIDS)
  pgrep -u agentuser -f "$EXECUTOR_PAT" 2>/dev/null | grep -v -x -F "$excl" | wc -l | tr -d " "; }
```

🔴 `PPid` брать из `/proc/PID/status`, а НЕ полем `$4` из `/proc/PID/stat`: у процесса с пробелом
в имени (`tmux: server`) поля stat съезжают, в `$4` попадает буква состояния, и обход предков
обрывается с `[: S: integer expression expected`.

🔴 `-x` к `pgrep` НЕ добавлять: дефолтный `EXECUTOR_PAT` — префикс (`claude --dangerously`),
при точном совпадении он не найдёт ничего, и перекос станет обратным — а недосчёт хуже пересчёта,
он поднимает ЛИШНЕГО исполнителя вместо того чтобы просто ждать.

Исправлено в `claude/wait_slot_and_launch.template.sh` и `claude/wait_conditions_and_launch.template.sh`
(бэкап до правки — `claude/_backup_selfcount_20260809_214639/`).

**Проверять правку только фактом «сколько реальных».** Мой первый «эталон»
(`ps | grep -x '.*claude --dangerously-skip-permissions' | wc -l`) сам себя не вычитал, показал 2
против верного 1 — и на секунду выглядело, будто исправленный счётчик недосчитывает. Эталон должен
исключать себя ровно так же, как проверяемая проба.

## 12. 🔴 Очередь, доделавшая свой список, держит tmux-сессию — «жив ли слот» по сессии считать нельзя (09.08.2026)

Прямое следствие #10. Ожидатель, который считает слоты по живым tmux-сессиям очередей (а не по
процессам исполнителей), выглядит надёжнее: он не ловит яму между концом одной задачи и стартом
следующей внутри одной очереди. Но идлящая очередь с исчерпанным `TASKS` сессию НЕ закрывает —
09.08 `shop_orch` держал сессию ещё долго после `T301 STATUS=SUCCESS`, и счёт «по сессиям» дал бы
«слот занят» навсегда, то есть вернул бы ровно ту пятичасовую яму, ради которой всё чинилось.

**Как правильно:** слот занят, если у очереди есть ЖИВОЙ исполнитель ИЛИ есть незакрытые задачи
из её списка. Пустая сессия без исполнителя и без незакрытых задач — свободный слот.
Признак закрытой задачи — строка `STATUS=` в её `orch/progress.md` и отчёт с валидным `STATUS:`.

## 13. 🔴 Кончилось место на диске Windows — виртуалка WSL встаёт ЦЕЛИКОМ, и RAM-сторож этого не видит (12.08.2026)

Ночная волна PROJECTA оборвалась 12.08 в 01:54 без единого предупреждения: все процессы остановились
одномоментно, отчёта нет, в логах — обрыв на полуслове.

файлу на стороне Windows.

`state=OK` — память отпадает), затем журнал Windows на предмет ошибок с кодом 112, затем

но возвращает блоки внутрь гостевой ФС — этого достаточно, чтобы файл перестал расти. Вернуть
место Windows можно только включив разрежённость и сжав образ, а это требует остановки WSL.

## 15. 🔴 `~/.git-credentials` под root — `git push` от агента падает молча (12.08.2026)

как протухший токен. Токен был в порядке: файл `/home/agentuser/.git-credentials` принадлежал **root**

🔴 **В приёмку задачи входит не только «коммит сделан», но и «запушено»:**
`git log --oneline @{u}..HEAD` должен быть пуст. Локальный коммит не переживает потерю машины.

## 16. 🔴 «Исполнители не коммитят» — это не лень, это ГОНКА в супервизоре (12.08.2026)

Пять задач подряд (T233, T234, T237, T244, T246) закрылись со `STATUS:`, но БЕЗ своего коммита:
работа лежала в рабочем дереве, а в отчёте на месте хеша стоял плейсхолдер `@@COMMIT@@` /
`__COMMIT_T246__`. Коммитили за них следующие задачи и человек. Требование при этом стояло в
ШАПКЕ каждого таск-файла, крупно и с 🔴 — и всё равно не выполнялось. Это и есть признак того, что
дело не в дисциплине.

**Корень — в двух правилах, которые противоречат друг другу:**

1. каждый таск-файл требует: «строку `STATUS:` писать ТОЛЬКО последним действием»;
2. `finish_on_report` в `claude_supervisor.template.sh` при появлении валидного `STATUS:`
   немедленно делает `kill_agent` и выходит.

Агент, планировавший «дописать отчёт → поставить STATUS → закоммитить», не доживает до третьего
шага: его снимают на втором. Требование «коммит — часть работы» при таком порядке физически
недостижимо, сколько его ни повторяй.

**Лечение — с двух сторон:**

- **Порядок в таск-файле и в `HOW_TO_RUN.md` («Финальный отчёт»):** сначала `git add/commit/push`,
  затем реальный хеш в отчёт, и ТОЛЬКО ПОТОМ строка `STATUS:`. Это дешевле любой автоматики.
- **Гейт в супервизоре (`COMMIT_GATE`, по умолчанию включён):** увидев `STATUS:` при грязном
  рабочем дереве ИЛИ плейсхолдере вместо хеша, супервизор один раз пишет агенту в его же REPL, что
  именно осталось, и ждёт `COMMIT_GRACE` (900 с). Не доделал — задача всё равно закрывается
  (висеть вечно нельзя), но с 🔴 в логе и пингом в TG. Агент мёртв — закрываем сразу, но тоже
  громко: человек должен узнать, что в дереве осталась незакоммиченная работа.

🔴 **Общий урок, шире git:** если требование повторяется в каждом таске и всё равно не
выполняется — ищи не мотивацию исполнителя, а механизм, который делает его невыполнимым.
Пять одинаковых «нарушений» подряд — это всегда дефект конвейера, а не пяти разных агентов.

**Итог первой боевой ночи гейта (12→13.08):** он сработал — трижды позвал, и агент трижды
послушался, включая «вписал фактический хеш вместо плейсхолдера». Но ВЕРДИКТ гейта был неверным:
условие «доведено» проверялось по ЧИСТОМУ ДЕРЕВУ репозитория, а репозиторий общий — в нём всегда
лежат файлы соседних задач и правки человека. Поэтому гейт трижды дождался конца `COMMIT_GRACE` и
написал «работа так и не в git», хотя работа была в git. Исправлено 13.08: признак «агент довёл
своё» — не чистое дерево, а **появившийся коммит** (HEAD на старте супервизора против HEAD сейчас);
грязное дерево осталось лишь поводом позвать. Плейсхолдер в отчёте — повод в любом случае.

🔴 **Вторая поправка того же дня (вечер 13.08): движение HEAD доказательством НЕ является.** Правка
выше убрала ложные срабатывания, но завела ложное МОЛЧАНИЕ: HEAD двигает не только исполнитель —
его двигают соседние задачи общей очереди и человек, коммитящий по ходу ЧУЖОЙ работы. Так прошёл
T248: работа исполнителя осталась незакоммиченной, гейт увидел чужой коммит, промолчал, и коммит
потом делал человек (`4c9f374`). Признак теперь — **коммит, трогающий САМ ФАЙЛ ОТЧЁТА**
(`git log BASE..HEAD -- <report>`): отчёт пишет только исполнитель, а предписанный порядок «коммит
и пуш → хеш в отчёт → `STATUS`» гарантирует, что такой коммит существует к моменту проверки.
Дописанные ПОСЛЕ коммита хеш и `STATUS` ложным срабатыванием не становятся — проверяется ФАКТ
коммита отчёта, а не чистота файла (иначе гейт звал бы на КАЖДОЙ задаче). Отчёт вне репозитория
или под `.gitignore` — признак недоступен, работаем по прежнему (сдвинулся HEAD, значит довёл).
Проверено семью сценариями до подмены файла; старая версия из них валит ровно один — тот самый
случай T248.

🔴 **Урок про сам гейт:** проверка «сделал ли ЭТОТ агент» обязана опираться на артефакт, который
кроме него никто не пишет. Любой общий показатель (чистота дерева, положение HEAD, время
последнего коммита) в общем репозитории меряет не его, а всех сразу — и врёт в обе стороны:
сначала ложной тревогой, после «починки» — ложным молчанием.

## 17. 🔴 «Закрыта ли задача» надо проверять ТАК ЖЕ ШИРОКО, как это делает супервизор (13.08.2026)

У супервизора есть ветка `REPORT-ALIAS`: исполнитель написал отчёт под сокращённым именем — он его
всё равно найдёт по номеру задачи и закроет её. У вотчдогов и очередей такой ветки часто НЕТ, они
ищут точное `report_<ПОЛНОЕ_ИМЯ_ТАСКА>.md`. Расхождение стоит дорого.

Кейс 12→13.08: `T235_loyalty_denezhnyj_defekt_peresborka` закрылся файлом
`report_T235_denezhnyj_defekt_peresborka.md` (без `loyalty_`), `T242_instrukciya_testirovshchiku_finalnaya`
— файлом `report_T242_instrukciya_testirovshchiku.md` (без `_finalnaya`). Обе задачи — `SUCCESS`.
Вотчдог их не нашёл, счёл незакрытыми и **в ближайшее разрешённое окно перезапустил бы обе поверх
уже сделанного**: пересборку инсталлятора и переотправку документов заказчику. Поймано случайно,
по строчке «ждут вечера» в логе, где этих задач быть не должно.

**Правило:** любая проверка «сделано ли» ищет `report_<НОМЕР>_*.md` с валидной строкой `STATUS:`,
а не точное имя. Нашёлся файл с другим именем — записать это в лог явной строкой `REPORT-ALIAS`,
чтобы человек видел расхождение и мог поправить имя, а не гадать.

🔴 Обратная сторона: раз имя отчёта не обязано совпадать, **номер задачи в имени файла становится
единственным ключом** — писать отчёт с чужим номером нельзя категорически, это закроет чужую задачу.

## 18. 🔴 «Кнопка в GUI не нажимается» — три разные причины, и все выглядят одинаково (13.08.2026)

Две задачи подряд встали на одном месте: не удавалось нажать кнопку в модальном окне, перебирались
способы нажатия (координаты из OCR, клик по якорю, `Enter`, `Left`+`Enter`), одна из задач в итоге
нажала `Escape` и **потеряла уже полученный результат**. Разбор показал: причин три, снаружи они
неотличимы, и ни одна не лечится перебором способа нажатия.

**Причина 1. Врал ВЕРДИКТ, а не клик.** Нажатие запускает синхронный серверный вызов; пока он идёт,
главный поток страницы стоит, и проверка «закрылось ли окно» получает таймаут. Замер: клик ДОШЁЛ
(результат появился), а драйвер в ту же секунду отрапортовал «не дошёл» — и следующая попытка
затирала сделанное. Исходов должно быть ТРИ, а не два: «окно ушло» / «страница ЗАНЯТА, значит клик
дошёл, ждём» / «окно на месте и страница отвечает — вот теперь действительно не дошёл».

**Причина 2. Окно осталось, но ИЗМЕНИЛОСЬ.** Многие платформы не закрывают диалог, когда действие
отбито проверкой, а дописывают в него сообщение. Сравнивать надо не только факт наличия окна, но и
его текст, иначе успех читается как провал.

**Причина 3 (главная). Кнопка ПЕРЕКРЫТА другим элементом.** У кнопки честный прямоугольник и
честный центр, но `document.elementFromPoint(центр)` возвращает чужой элемент — панель сообщений,
всплывшая поверх командной панели. Клик по центру уходит в неё, и доверенным событием, и настоящим
указателем. Снаружи неотличимо от «кнопка мёртвая».
Лечение: **hit-тест перед кликом**; центр перекрыт — искать свободную точку внутри самого
прямоугольника кнопки (сетка 5×5); свободной точки нет — не кликать вслепую, а НАЗВАТЬ
перекрывающий элемент и уйти на запасной вход (горячая клавиша кнопки, взятая из её двойника
в меню, с предварительным захватом фокуса кликом в свободную точку).

🔴 **Методический вывод, шире GUI:** когда способ не срабатывает, перебирают обычно СПОСОБ. А
проверять надо было ТОЧКУ и ВЕРДИКТ. Признак, что вы в этой ловушке: перебрано четыре и более
вариантов одного действия, все «не работают» одинаково молча, а человек делает то же самое мышью
за секунду.

🔴 **И отдельно про опознание окон:** селектор «по началу id» может не находить целый класс окон
(вложенные формы), хотя окно на экране есть, а разведка честно отвечает «окна нет». Ловить по
устойчивому признаку (класс + хвост id), и проверять приём НЕ НА ОДНОМ окне: подгонка под
единственный кадр — самая частая причина того, что «у меня работало».

## 19. 🔴 Тихая смерть канала уведомлений: `local a=$1 b="$RATE.$a"` при `set -u` (14.08.2026)

Вотчдог очереди отказался поднимать волну по гейту памяти — и тут же упал:

```
[09:27:43] RAM 819Mi < 1800Mi — не поднимаю
loyalty_watchdog.sh: line 64: k: unbound variable
```

Виновата одна строка, прожившая в скрипте неделю:

```bash
tg_rate(){ local k=$1 m=$2 f="$RATE.$k" now; ... }     # ← ловушка
tg_rate(){ local k="$1" m="$2" now                      # ← как надо
  local f="$RATE.$k"; ... }
```

🔴 **Bash раскрывает ВСЕ слова команды `local` ДО того, как выполнит хоть одно присваивание.**
Поэтому `$k` в третьем слове ещё не существует; без `set -u` это дало бы пустую строку и молчаливо
неверное имя файла, с `set -u` — фатальную ошибку. Присваивание, ссылающееся на соседа по той же
`local`/`declare`/`export`, не работает никогда — это не про порядок слева направо.

**Почему цена высокая.** Функция была `tg_rate` — единственный путь ВСЕХ предупреждений владельцу:
нехватка RAM, нехватка места на диске, задача в карантине. То есть отказ убивал ровно тот канал,
по которому о нём и должны были сообщить. Снаружи это выглядело как тишина: в логе оставалась
строка `say` перед вызовом, а пинга не приходило — и «пингов нет» неотличимо от «поводов не было».

🔴 **Вывод шире bash: путь уведомления обязан быть проверен СРАБАТЫВАНИЕМ, а не чтением кода.**
Один раз искусственно создайте повод (опустите порог, подсуньте флаг карантина) и убедитесь, что
сообщение реально пришло. Всё, что сообщает о сбоях, отказывает бесшумно по определению: его
поломка не создаёт события, о котором можно было бы сообщить.

## 20. 🔴 Тишина транскрипта — не диагноз: у неё минимум три причины (15.08.2026)

За одни сутки конвейер дважды потратил на разные болезни одно и то же лекарство — ожидание:

* **T257** — агент замолчал, супервизор честно отждал `STALL_LIMIT`, снял его и отправил задачу в
  карантин. Работа за 16 минут уцелела только потому, что человек это заметил.
* **T259** — в панели агента висело `API Error: Unable to connect to API (ENOTIMP)`. Агент простоял
  **1 час 12 минут**, транскрипт молчал, до снятия по таймауту оставалось ещё полчаса. Разбудил
  человек ОДНИМ сообщением в панель — и задача поехала дальше. Тот же текст 04.08 унёс T165.

Со стороны супервизора все три состояния выглядят ОДИНАКОВО — молчащим jsonl:

| что на самом деле | что видит супервизор | что правильно делать |
|---|---|---|
| агент думает над длинной командой | тишина | **ждать**, снимать нельзя |
| агент стоит на ошибке связи | тишина | **будить**, ждать бессмысленно — сам не оживёт |
| агент умер | тишина | снимать и перезапускать |

🔴 **Вывод: конвейер обязан различать причины тишины, иначе он тратит на каждую одинаковые полтора
часа — и ночью это стоит целого окна.** Один таймер на все случаи — это не «надёжно», это отказ от
диагностики. Второй признак берётся не из транскрипта, а рядом с ним: панель REPL показывает, стоит
ли агент на ошибке связи, — и решение принимается по СОВПАДЕНИЮ двух признаков (строка ошибки в
панели И тишина дольше `API_ERROR_QUIET`). По одному признаку срабатывать нельзя: те же слова агент
печатает в собственном выводе (`fetch failed` в этом репозитории — штатная строка лога моста киоска).

Реализация: `claude_supervisor.template.sh`, `classify_pane` → `RATE_LIMIT | API_ERROR | NONE`,
побудка в панель, `API_ERROR_TRIES` попыток, затем закрытие по прежнему пути зависшего агента —
но с явной причиной в логе. Проверка: `supervisor_api_error_selftest.sh` (образцы панели + стенд
с настоящим супервизором). Лимит сессии остаётся ОТДЕЛЬНОЙ веткой со своей логикой ожидания.

🔴 **Побочное, но более важное открытие T263 — почему T259 не разбудил себя сам.** В tmux 3.4
префикс `=` (точное имя) понимают только таргеты СЕССИИ и ОКНА. Командам, которым нужен таргет
ПАНЕЛИ, `-t "=имя"` даёт `can't find pane` и код 1:

```
tmux capture-pane -p -t "=sess"   -> can't find pane: =sess     (пусто!)
tmux capture-pane -p -t "=sess:"  -> содержимое панели          (работает)
tmux send-keys    -t "=sess"      -> rc=1, ничего не доставлено
tmux send-keys    -t "=sess:"     -> rc=0, текст в панели
```

С `2>/dev/null` это отказывает молча. У супервизора из-за одной этой формы `pane_tail` всегда
возвращал пусто (**ветка RATE-LIMIT не могла сработать ни разу**), а `remind_commit`/`remind_report`
писали в лог «напоминание отправлено», не отправив ничего. Лончер уцелел случайно — он шлёт промпт
без `=`. 🔴 Правило: у любой tmux-команды проверяй, какой таргет она ждёт — панель, окно или сессию;
одна и та же строка «=имя» в одном месте законна, а в соседнем — тихий отказ.

## 20а. 🔴 Механизм был написан, прошёл самотест — и не работал 23 дня: его перехватывала ветка выше (07.09.2026)

Продолжение пункта 20. Детектор ошибки связи завели 15.08 (T263), он прошёл 41 проверку самотеста
и после этого **ни разу не сработал на живой задаче**. 07.09 агент T339 простоял на
`API Error: Unable to connect to API (ENOTIMP)` **1 час 11 минут**, толкать его снова пришлось
человеку. В журнале супервизора за всё это время не было ни одной строки со словом API — не
«сработал неверно», а не звался вовсе.

Причина — порядок проверок в главном цикле:

```bash
if resolve_report; then
  finish_on_report; rc=$?
  if [ "$rc" -eq 11 ]; then continue; fi   # <- черновик отчёта: выход из витка ЗДЕСЬ
  ...
fi
...
if handle_api_error "$AGE"; then continue; fi   # <- сюда не доходило никогда
```

Ветка `rc=11` — «отчёт без STATUS у живого агента» — заведена 10.08 и совершенно правильная сама
по себе. Но **все наши таск-файлы требуют вести отчёт ПО ХОДУ**, то есть файл отчёта появляется в
первые минуты работы. Дальше каждый виток цикла заканчивался на ней, и детектор связи оставался
за спиной. Он срабатывал бы только у задачи, которая отчёт ещё не создала, — то есть почти ни у
какой.

🔴 **Правило: самотест механизма не доказывает, что механизм ЗОВЁТСЯ.** D-стенды поднимали
настоящий супервизор, но ни один из них не создавал файл отчёта — а именно его наличие и отключало
проверку. Стенд проверял функцию, а не путь к ней. Когда пишете стенд на «сложную ветку», задайте
себе отдельный вопрос: какие ЕЩЁ условия выполняются у реальной задачи в этот момент, и не уводят
ли они управление раньше.

🔴 **Второе правило, про диагностику:** «супервизор пишет, что агент жив» — не значит, что агент
работает. Строка `report без STATUS, но агент ЖИВ и пишет` печаталась каждые десять секунд, пока
агент неподвижно стоял на ошибке. Живой процесс и растущий возраст транскрипта — разные вещи.

Исправлено: у черновика сначала спрашиваем панель (`handle_api_error`), потом ждём дальше.
Регресс закрыт стендом **D5** в `supervisor_api_error_selftest.sh` — он поднимает супервизор,
создаёт черновик отчёта уже ПОСЛЕ старта (как в жизни) и ждёт побудки. Проверено обеими сторонами:
на исправленном шаблоне D5 проходит, на прежнем — падает.

## 🔴 Две очереди в ОДНОМ PROJECT_DIR делят state/ и душат друг друга через MAX_PARALLEL (04.09.2026)

Симптом: вторая очередь, поднятая в том же каталоге проекта, стартует и **молча выходит с кодом 0**
— ни строки в логе, ни сессии исполнителя, tmux-сессия самой очереди тоже исчезает. Выглядит как
«tmux не создал сессию» или «скрипт упал», и час уходит на поиски несуществующей ошибки запуска.

Причина: `active_count()` считает активные сессии по `$STATE_DIR/*.session` ЦЕЛИКОМ, не различая,
какая очередь их создала. Обе очереди указывают на один `PROJECT_DIR`, значит и на один `state/`.
При `MAX_PARALLEL=1` работающая задача первой очереди занимает единственный слот, и вторая честно
считает, что параллель исчерпана.

Как это выглядело 04.09: ветка документов вела T325, ветка ядра с `TASKS=T330` не поднималась
вообще. Стоило семи минут ночного окна и выглядело как сбой tmux.

Что делать:
- поднимая ВТОРУЮ очередь в том же `PROJECT_DIR`, задавать `MAX_PARALLEL` с учётом уже работающих
  задач (две ветки → `MAX_PARALLEL=2`), иначе она не возьмёт ничего;
- 🔴 и тогда ОБЯЗАТЕЛЬНО ограничивать её списком `TASKS` до ОДНОЙ задачи, если задачи правят общий
  файл: поднятый лимит разрешит ей взять сразу две, и второй агент затрёт правки первого.
  Следующую задачу поднимать реле после закрытия предыдущей;
- либо разносить ветки по разным `PROJECT_DIR` со своими `state/` — но тогда разъезжаются
  progress.md и отчёты, что для одного проекта неудобно.

## 🔴 Параллельный исполнитель СНОСИТ чужую работу широким `git add` (04→05.09.2026)

Симптом: две задачи шли параллельно, обе закрылись успешно, обе довольны. А в репозитории работы
одной из них НЕТ — коммит второй её удалил. На диске файлы при этом целы, поэтому ни один агент
ничего не заподозрил: они смотрят на дерево, а не на историю.

Как это выглядело: T333 создала сервис (`ksobio.cs` +767 строк, шесть новых файлов) и закоммитила
в 20:0x. Через час T330 сделала свой коммит и **удалила всё это из репозитория**: у неё в дереве
лежало состояние ДО коммита T333, и `git add` по каталогу захватил старые версии чужих файлов.
Заодно откатились 19 отчётов и журналов других задач.

Почему обе задачи не заметили: каждая проверяла СВОЮ зону («git status чист по моей зоне») — а
пострадала чужая. Обе прошли приёмку честно.

Что делать:
- 🔴 **добавлять в индекс только СВОИ файлы, поимённо.** `git add <каталог>` и тем более `git add -A`
  в параллельной работе — это не удобство, а способ снести соседа;
- 🔴 **перед коммитом сверять, не откатываешь ли чужое:** `git diff --cached --stat` и посмотреть,
  нет ли в списке файлов, которых задача не трогала. Крупный минус у чужого файла — стоп;
- проверка после параллельной волны (делать оркестратору, а не исполнителю): по каждому файлу
  сравнить дерево и HEAD, крупная разница = откат. Быстрый вид:
  `git status --porcelain | grep '^ M'` и для подозрительных
  `git show HEAD:<файл> | wc -l` против `wc -l <файл>`;
- восстанавливается просто, пока дерево цело: `git add` нужных файлов и коммит. Но если бы VM
  упала между откатом и обнаружением, работа исчезла бы совсем.

## 21. 🔴 REPORT-ALIAS брал отчёт СОСЕДА по параллельной очереди и снимал живого исполнителя (10.09.2026)

Супервизор умеет находить отчёт, названный не так, как ждала очередь (фикс 30.07, кейс T121). У
поиска два захода: строгий — `report_<номер нашей задачи>_*.md`, и запасной — любой свежий
`report_*.md`, где есть И строка `STATUS:`, И имя нашей задачи в тексте. Считалось, что двух
признаков достаточно, чтобы не утащить чужое.

**Недостаточно.** 10.09.2026 в очереди лояльности параллельно шли T366 (установка расширения в
боевую) и T367 (фронт). T367 закончила раньше и в своём отчёте написала честную строку «чужого не
трогал: ops T366_ustanovka_yadra_dnyom». Этого ОДНОГО упоминания хватило:

```
05:39:17 REPORT-ALIAS: ожидали report_T366_ustanovka_yadra_dnyom.md,
                       нашли report_T367_front_atomarnyy_metod.md со строкой STATUS → работаем по нему
05:39:58 DONE-NOT-SUCCESS STATUS=PARTIAL
```

Супервизор закрыл T366 чужим статусом и снял её исполнителя на 18-й минуте — посреди установки
расширения в БОЕВУЮ базу. Работа при этом была сделана (расширение встало, точка отката снята), но
отчёта не осталось вовсе, и задача ушла в карантин `.ambiguous`.

**Фикс:** отчёт, чьё ИМЯ несёт чужой номер задачи (`report_T<другой>_*`), не берётся никогда,
сколько бы раз он ни упоминал нас в тексте. Имя файла — признак владения, текст — нет.
Свой отчёт под сокращённым именем (исходный кейс T121) по-прежнему находится первым заходом.

**Урок шире оснастки:** чем аккуратнее исполнители пишут «чужого не трогал, зона такая-то», тем
чаще их отчёты упоминают соседей по имени. Эвристика, опирающаяся на текст отчёта, от хорошей
дисциплины ломается чаще, а не реже.

## 22. 🔴 Гейт грязного дерева наказывал за ЧУЖУЮ грязь: 64 срабатывания, в свежих — сплошь соседи (10.09.2026)

Гейт (22.08.2026) понижает `SUCCESS` до `PARTIAL`, если после закрытия задачи в рабочем дереве есть
незакоммиченное. Смысл верный: задача не считается сделанной, пока работа не в git.

**Мерил он не то.** Условие было «грязно ВСЁ дерево», а дерево общее: рядом работают другие
исполнители, оркестратор пишет свой журнал, человек правит документацию. Замер по логам на
10.09.2026 — **64 срабатывания**, и в свежих списках наказанной задаче не принадлежит ни один файл:

```
T357 (ОРП на третьей кассе) понижена за:
    progress.md; t352_klyuchi_vip.ps1; t355_diag.ps1; t355_patch.py
T353 (гард остатков)        понижена за:
    loyalty/app/src/screens/admin/*.jsx; t356_node_install.sh; report_T351...
```

Отдельно показательно: в списке почти всегда `orch/*/orch/progress.md` — **журнал самого
оркестратора**. Машинерия пишет его сама, никто не коммитит сразу, значит гейт срабатывал почти в
каждой волне по умолчанию.

Итог: сигнал превратился в шум, а шум вредный — `PARTIAL` в обиходе означает «не закрыто, надо
доделать», по нему задачи переоткрывают и перезапускают. Шестьдесят четыре повода не доверять
статусам.

**Фикс:** гейт меряет **ПРИРОСТ**, а не грязь вообще.
- на старте задачи (`start_task`) снимается базовая отметка `state/<task>.dirtybase` —
  что было грязным ДО того, как исполнитель начал;
- при закрытии понижает статус только то, что появилось ПОСЛЕ старта;
- старая грязь не теряется: печатается отдельной строкой `DIRTY-TREE-OLD` как информация;
- служебные файлы машинерии (`progress.md`, `ORCH_STOP`, `WAVE_ON`) исключены совсем
  (`GIT_DIRTY_MACHINERY_RE`);
- базы нет (задача из прошлой жизни очереди) — поведение прежнее, как было.

**Почему НЕ «сузить до зоны задачи»** (рассматривалось и отклонено): зона в таск-файле написана
прозой, машинно не читается, любая формализация будет врать. И главное — так пролезет настоящий
промах: агент нахимичил ВНЕ своей зоны и не закоммитил, а гейт молчит. Ложная тревога поменялась бы
на пропуск дефекта, что хуже.

**Что осталось честным остатком:** параллельный сосед может нагрязнить в чужое окно, и виноватым
окажется не тот. Полностью это решается только пофайловым учётом «кто писал», которого у нас нет.

Напоминание-нудж в супервизоре (`COMMIT_GATE`) не трогали: он спрашивает другое — «сделал ли агент
СВОЙ коммит с отчётом» — и работает правильно.
