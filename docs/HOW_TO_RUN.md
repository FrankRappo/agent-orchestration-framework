# Запуск агентов Claude от пользователя agentuser

## Проблема

Claude Code (`claude --dangerously-skip-permissions`) не работает от root.
Текущая сессия запущена от root → нужно запускать агентов от agentuser.

Обычные `su`, `sudo -u`, `runuser` **не работают** — CLI определяет root-контекст
через переменные окружения (SUDO_USER и т.п.).

## Рабочий способ

`runuser` + `env -i` (чистое окружение без переменных от root) + `setsid` (отдельная сессия).

### 1. Подготовка

```bash
# Права на файлы (обязательно перед каждым запуском)
chmod -R 777 /work/projecth/

# Логи должны принадлежать agentuser
touch /work/projecth/tasks/A1_output.log
chown agentuser:agentuser /work/projecth/tasks/A*_output.log
chmod 666 /work/projecth/tasks/A*_output.log
```

### 2. Скрипт-лаунчер (launch_all.sh)

```bash
#!/bin/bash
cd /work/projecth

claude --dangerously-skip-permissions -p "$(cat tasks/A1_ui_form.md)" > tasks/A1_output.log 2>&1 &
claude --dangerously-skip-permissions -p "$(cat tasks/A2_api_endpoints.md)" > tasks/A2_output.log 2>&1 &
claude --dangerously-skip-permissions -p "$(cat tasks/A3_quiquo_e2e_test.md)" > tasks/A3_output.log 2>&1 &

echo "3 agents launched, PIDs: $(jobs -p)"
wait
echo "All done"
```

### 3. Запуск

```bash
setsid runuser -u agentuser -- env -i \
  HOME=/home/agentuser \
  PATH="/usr/local/bin:/usr/bin:/bin" \
  SHELL=/bin/bash \
  /work/projecth/tasks/launch_all.sh &>/tmp/launch_all.log &
```

Ключевые элементы:
- `setsid` — создаёт новую сессию, отвязывает от root-терминала
- `runuser -u agentuser` — запускает от agentuser (не требует пароль)
- `env -i` — **обязательно** — очищает ВСЕ переменные окружения
- `HOME`, `PATH`, `SHELL` — минимальный набор переменных для работы claude

### 4. Запуск одного таска

```bash
setsid runuser -u agentuser -- env -i \
  HOME=/home/agentuser \
  PATH="/usr/local/bin:/usr/bin:/bin" \
  SHELL=/bin/bash \
  bash -c 'cd /work/projecth && claude --dangerously-skip-permissions -p "$(cat tasks/A1_ui_form.md)" > tasks/A1_output.log 2>&1' &
```

> ## 🔴 АГЕНТЫ РАБОТАЮТ ОТ agentuser — следствия (резюме, на которых уже спотыкались)
>
> Все sub-агенты и оркестраторы запускаются от **agentuser** (root не может `--dangerously-skip-permissions`).
> Практические выводы:
>
> 1. **Хелпер-скрипты, которые вызывает САМ агент, НЕ должны содержать `runuser`.** `runuser -u agentuser`
>    требует root, а агент УЖЕ agentuser → PAM не пустит вложенный `runuser` (см. §9.4). Скрипт, написанный
>    «от root» (с `runuser`/`pkill`/подъёмом X-стека), агент запустить не сможет — он молча упадёт.
>    Делай для агента отдельную версию без `runuser`, работающую напрямую (`DISPLAY=:NN scrot/xdotool …`),
>    а операции, которым нужен root (поднять/убить Xvfb/VNC, `pkill`), выноси во **внешний root-процесс**
>    (stack-keeper в своём tmux). Агент — только «глаза+руки» внутри уже поднятого стека.
>    Пример (PROJECTA, 2026-06-18): драйвер AnyDesk-экрана `:99` в двух версиях —
>    `/work/remote_tools/anydesk_projecta.sh` (от ROOT: `up/down`, внутри `runuser`) и
>    `/work/remote_tools/anydesk_projecta_agentuser.sh` (ДЛЯ АГЕНТА: `scrot/xdotool` напрямую, без `runuser`).
>
> 2. **Лог агента и все каталоги записи должны быть agentuser-овскими — иначе МГНОВЕННАЯ тихая смерть.**
>    Если launcher/supervisor (от root) создаёт `output.log` через `: > LOG` — файл root-овский 644,
>    и `exec claude … > LOG` от agentuser падает на «permission denied». claude умирает в первые секунды
>    с **пустым логом**, но PID успевает записаться (echo `$$` идёт до `exec`) → со стороны выглядит как
>    «launch не дал живого PID» / «launch не стартовал», причём лог пуст и диагностировать нечем.
>    Лечение: сразу после создания лога — `chown agentuser:agentuser "$LOG"; chmod 666 "$LOG"` (root может), а
>    каталоги скринов/отчётов — `chmod -R 777` или `chown -R agentuser`. (Это частный случай грабли
>    «Permission denied на лог-файлы» из таблицы выше, но проявляется особенно коварно для агента.)
>
> 3. **Для лончера агента надёжнее arg-форма** `exec claude … -p "$(cat task.md)"` (single-level eval,
>    backticks/`$()` из содержимого файла НЕ реевалюируются — безопасно), чем возиться со stdin-редиректом.

## Мониторинг

### Проверка процессов

```bash
ps aux | grep 'claude' | grep agentuser | grep -v grep | grep -v session_saver
```

### Размер логов (растёт = агент работает)

```bash
wc -c /work/projecth/tasks/A*_output.log
```

**Важно:** в режиме `-p` лог пишется целиком в конце работы.
Пока агент работает — файл пустой (0 байт). Это нормально.

### Автоматический мониторинг (цикл)

```bash
while true; do
  count=$(ps aux | grep 'claude' | grep agentuser | grep -v grep | grep -v session_saver | wc -l)
  sizes=$(wc -c /work/projecth/tasks/A*_output.log 2>/dev/null | tail -1)
  echo "[$(date +%H:%M:%S)] agents: $count | logs: $sizes"
  [ "$count" -eq 0 ] && echo "All done!" && break
  sleep 30
done
```

### Чтение результатов

```bash

cat /work/projecth/tasks/A2_output.log
```

## Частые ошибки

| Ошибка | Причина | Решение |
|--------|---------|---------|
| `--dangerously-skip-permissions cannot be used with root/sudo` | Переменные окружения от root | Добавить `env -i` |
| `Permission denied` на лог-файлы | Файлы принадлежат root | `chown agentuser:agentuser` + `chmod 666` |
| Логи пустые, процессы идут | Нормальное поведение `-p` | Ждать завершения |
| Агент не видит docker | agentuser не в группе docker | `usermod -aG docker agentuser` (уже сделано) |
| Bash exit 1 даже на `true`/`echo`, Grep/Glob = `EACCES` на ripgrep | CWD унаследован `/root` (или другой root-owned 700 каталог), agentuser туда не имеет доступа | В `bash -c` обязательно `cd /work/<проект> && claude …` |
| `rg: command not found` внутри агента | PATH в `env -i` не включает `~/.local/bin` / `~/.cargo/bin` agentuser'а | `PATH="/home/agentuser/.local/bin:/home/agentuser/.cargo/bin:/usr/local/bin:/usr/bin:/bin"` |
| Агент умирает сразу после старта launcher'а | Унаследовал stdin/stdout от parent-скрипта → SIGPIPE после exit | Добавить `</dev/null >/dev/null 2>&1` к строке `setsid runuser …` перед `&` |
| Лог launcher'а полон `command not found`, `syntax error near '('`, `bd55284: command not found` сразу после старта | **Backtick / `$()` / `$VAR` интерполяция prompt'а внешним bash'ом.** Если launcher делает `bash -c "... claude -p \"$PROMPT\" ..."` (двойные кавычки) — outer bash раскрывает `$PROMPT`, и backticks/`$(…)` из содержимого `.md` prompt'а выполняются как command substitution ДО того как claude вообще стартует | Использовать **single-quoted bash -c** + read prompt внутри: `bash -c 'cd "'"$PROJECT_DIR"'" && exec claude --dangerously-skip-permissions -p "$(cat "'"$TASK_FILE"'")"'`. Или ещё проще — **stdin redirect**: `bash -c 'cd "'"$PROJECT_DIR"'" && exec claude --dangerously-skip-permissions -p < "'"$TASK_FILE"'"'` (как в `tasks_runner.template.sh`). Селективная интерполяция переменных через `'...'"$VAR"'...'` |

### Безопасный one-liner launcher (избегаем double-eval prompt'а)

**Контекст-кейс (projectd 2026-05-27 07:51):** `launch_orchestrator.sh` использовал паттерн `bash -c "... -p \"$ORCH_PROMPT\""` (двойные кавычки) — outer bash раскрыл `$ORCH_PROMPT`, и backticks из markdown code-fence'ов prompt'а выполнились как `$(...)` command substitution. Лог наполнился `command not found`, `syntax error near '('`, и `claude -p` даже не запустился — получил `Error: Input must be provided either through stdin or as a prompt argument`. PID процесса был создан, но реального claude не было.

**Правило:** в one-liner launcher'е через `setsid runuser -- bash -c '...'` **prompt никогда не интерполируется outer bash'ом**. Только filename переменные:

❌ **Опасно** (двойные кавычки вокруг bash -c → outer eval):
```bash
PROMPT=$(cat task.md)
setsid runuser -u agentuser -- env -i ... bash -c "claude -p \"$PROMPT\""   # ← outer bash раскроет $PROMPT и выполнит backticks
```

✅ **Безопасно** (single-quoted bash -c + read внутри):
```bash
setsid runuser -u agentuser -- env -i ... bash -c '
  cd "'"$PROJECT_DIR"'" &&
  exec claude --dangerously-skip-permissions -p "$(cat "'"$TASK_FILE"'")"
'
```

✅ **Ещё проще** (stdin redirect, нет вообще проблемы со spec.symbols):
```bash
setsid runuser -u agentuser -- env -i ... bash -c '
  cd "'"$PROJECT_DIR"'" &&
  exec claude --dangerously-skip-permissions -p < "'"$TASK_FILE"'"
'
```

Паттерн `'...'"$VAR"'...'` — селективная интерполяция: одинарные кавычки запрещают раскрытие, между ними короткий двойной-кавычковый сегмент с конкретной переменной. Это позволяет body bash-команды быть literal, а filename'ы — динамическими.

**Альтернатива** — спрятать всё в self-contained shell-скрипт (как `launch_all.sh` в §2), который запускается одной строкой. Внутри скрипта `claude -p "$(cat task.md)"` работает корректно — там single-level eval, без вложенности.

## Универсальные уроки из параллельных запусков

Правила общего характера — применимы к любому проекту, не только DarkHaven. Проект-специфичные грабли (git stash + venv, merge через worktree, ключ push'а, миграции в `__pycache__`, venv rebuild) живут в `workflow.md` соответствующего проекта.

### 1. Upload больших файлов — всегда с timeout и лимитом попыток

Агент может часами висеть на `scp`/`rsync`/`wget`, если сеть нестабильная, а output-лог при `-p` пустой — со стороны не видно, что он застрял.

**Правило для таск-файлов:**
- Внутренний timeout: `-o ConnectTimeout=20 -o ServerAliveInterval=10 -o ServerAliveCountMax=3` для `scp`/`ssh`
- Внешний timeout: `timeout 300 scp …`
- После 2-3 неудач — агент должен **остановиться и передать задачу пользователю**, не крутиться бесконечно
- Если файл можно **сгенерировать на целевой стороне** (например, ffmpeg `mp4 → webm` прямо на сервере) — это надёжнее, чем гнать через медленный линк

### 2. Мониторинг зависших агентов

Признак зависания: `wc -c output.log` = 0 **и** агент работает ≥45 мин.

```bash
# Диагностика
lsof -p <PID> | grep -E 'REG|TCP|pipe' | head
pgrep -P <PID> -a       # дочерние процессы
```

Если видно бесконечный retry на один ресурс (scp/curl/ssh) — **убить и разобраться**, не ждать сутки.

### 3. Остановка агента — строго сверху дерева

```bash
kill <runuser_PID>               # каскадно умрёт всё дерево
sleep 2
pkill -9 -f 'claude --dangerously'  # зачистка зомби
pkill -9 -f 'puppeteer_dev_chrome_profile-<ID>'  # orphan chromium, если был
```

### 3.5. ⚠️ Monitor — anti-patterns + правильный паттерн

**Контекст-кейс (projectd T31b, 2026-05-27 19:01):** sub-агент 30 мин писал log = 0 байт. Я предположил silent API timeout, послал `kill -9` тимы wrapper'у. Через ~10 сек оркестратор увидел уведомление от Monitor: «T31-DEAD without report». Но **через минуту обнаружил** что `T31_mobile_report.md` (42 KB, 464 строки, очень детальный отчёт) лежит на диске с timestamp 19:01 — записан **буквально в момент моего kill'а**. Агент НЕ был мёртвым, он флашил большой отчёт.

**Урок:** `claude -p` буферизует stdout до завершения. Log = 0 не означает «зависает» — он может *писать на диск* (Edit/Write tool) и при этом не показывать stdout. Прежде чем kill — проверить:
1. `pstree -p <PID>` — дочерние процессы есть? bash/node/curl/python = живой
2. `lsof -p <PID> 2>/dev/null | grep -E 'tasks/T.*\.md|reports/T.*\.md'` — пишет ли в свой report
3. `ls -lah /work/projectc/reports/` — есть ли свежие edits (date в пределах минуты)
4. State из `/proc/<PID>/status`: `R` (running) или `S` (sleeping = ждёт I/O, может ждать API turn'а) vs `Z` (zombie)

#### ❌ Anti-pattern: Monitor завязан на PID-alive

```bash
# ПЛОХО — race condition между PID-death и file-write
until [ -f reports/REPORT.md ] || ! kill -0 $PID 2>/dev/null; do sleep 30; done
```

Если кто-то (включая тебя самого) пошлёт kill — Monitor exit'нет до того как агент закончит flush. Сообщит «DEAD without report», хотя файл появится через секунды.

#### ✅ Правильный паттерн 1 — file-only с timeout

```bash
# Ждём ТОЛЬКО появление файла. PID-death игнорируем.
# Timeout настраивается через Monitor.timeout_ms — Monitor сам прекратит работу.
until [ -f reports/REPORT.md ]; do sleep 30; done; echo "DONE: $(wc -l < reports/REPORT.md) lines"
```

Если Monitor истёк по `timeout_ms` без сигнала — re-arm. Если PID давно мёртв но файл есть — всё хорошо, Monitor поймает file-existence. Если PID мёртв и файла нет дольше разумного — re-arm-not-needed, действуй вручную (грозный сигнал по chat'у).

#### ✅ Правильный паттерн 2 — grace period перед kill

Если **обязательно** убить:

```bash
# 1. SIGTERM (даёт агенту flush)
kill <PID>
# 2. 30s grace
for i in {1..30}; do kill -0 <PID> 2>/dev/null || break; sleep 1; done
# 3. Если ещё жив — финальный SIGKILL
kill -0 <PID> 2>/dev/null && kill -9 <PID>
# 4. Перед declared DEAD — финальная проверка filesystem
sleep 3 && ls -la reports/REPORT.md 2>/dev/null
```

#### ✅ Правильный паттерн 3 — Monitor «success only»

Для observe-only тасков (тур, ревью, доку) лучше Monitor НЕ завязан на PID:

```bash
# Только file-existence. PID живой/мёртвый — Monitor игнорирует.
# Если файл не появится за timeout_ms — Monitor умрёт по timeout,
# и ты пересмотришь решение (re-arm с увеличенным timeout, или ручная инспекция).
until [ -f reports/REPORT.md ]; do sleep 30; done
echo "FILE: $(stat -c '%y %s' reports/REPORT.md)"
```

#### Когда `until ! kill -0 PID` всё-таки OK

Только если задача **обязана** что-то деплоить и нужно поймать crash до deploy'а. Тогда добавь `sleep 3` после `! kill -0` и **finальный recheck file** перед declared DEAD. Иначе race.

### 4. Дедупликация алертов (cron-скрипты)

Если агент ставит периодический скрипт (cron), хэш-дедуп должен быть **качественным** (набор категорий проблем), а не включать числовые метрики. Иначе числа плавают каждый прогон → хэш меняется → алерт-спам.

```bash
# ПРАВИЛЬНО — срезать числовые значения sed'ом перед хешированием:
HASH_INPUT=$(echo "$ISSUES" | tr ' ' '\n' | sed -E 's/=[0-9.]+s?/=X/g' | sort -u | tr '\n' ' ')
STATE_HASH=$(echo "$SEVERITY|$HASH_INPUT" | sha256sum | cut -c1-16)

# НЕПРАВИЛЬНО — включает меняющиеся числа:
STATE_HASH=$(echo "$ISSUES" | sha256sum | cut -c1-16)
```

### 5. Сломался штатный путь? СТОП — не обходить

Если стандартный инструмент падает (Django `migrate` / `npm install` / `cargo build` / `terraform plan` и т.п.) — агент **обязан остановиться и передать задачу пользователю**. НЕЛЬЗЯ:

- применять schema-изменения напрямую (`ALTER TABLE`, `UPDATE/INSERT` в служебные таблицы типа `django_migrations`, `alembic_version`, `schema_migrations`)
- редактировать lockfile'ы вручную (`package-lock.json`, `poetry.lock`, `Cargo.lock`, `Gemfile.lock`, `yarn.lock`)
- прокидывать `--force` / `--no-verify` / `--ignore-scripts` / `--skip-checks` / `--fake` (для миграций) чтобы «просто продолжить»
- писать в `__pycache__/*.pyc`, `.next/`, `dist/`, `node_modules/.cache/` и другие кэши, которые считаются «производными»

Правило: если сломано — это сигнал о несогласованности между кодом, репо и состоянием системы. **Агент не должен ремонтировать обход самостоятельно** — рискует потерять данные или истину о состоянии, которую никто потом не восстановит.

**Пример (кейс DarkHaven, 2026-04-24):** агент watermark наткнулся на broken migration chain (`KeyError: ('shop', 'message')` — потерянный файл миграции). Вместо остановки сделал `ALTER TABLE shop_productimage ADD COLUMN watermark_applied` + `INSERT INTO django_migrations (app, name, applied)`. Колонка появилась, запись была в логе — но Django state-graph остался broken, следующий агент тоже страдал. Правильное действие: упасть и написать пользователю «`migrate` упал с X, не могу продолжать».

### 5.5. 🔴 ВИЗУАЛЬНАЯ ВЕРИФИКАЦИЯ — нельзя подменять синтетическими DOM-проверками

**Контекст-кейс (projectb T-CHECKOUT-FIX2, 2026-05-21):** агент сделал visibility-controller для 3 виджетов чекаута + geo-propagation, прогнал свой puppeteer-скрипт через 12 кейсов (4 города × 3 shipping), отчитался «**12/12 PASS**» и закрыл таск. Заказчица через 1.5 часа прислала **5 скринов с тремя живыми багами**: при выборе СДЭК всё ещё видна карта Я.Доставки, Я.Доставка-виджет показывает Ульяновск/Москву вместо выбранного <CITY>, СДЭК-виджет — пустой белый контейнер. Все три бага видны **на собственных скринах агента**, если их открыть глазами. Агент их не открывал — он проверял только синтетические признаки (`getComputedStyle().display !== 'none'`, `window-config readback`), которые проходили `assert`-ами, но **не соответствовали тому что покупатель реально видит**.

#### Правило

**Если таск производит скриншоты как доказательство «работает / не работает» — агент ОБЯЗАН открыть каждый скриншот через Read-tool и описать словами что на нём изображено, ДО того как ставить статус «PASS» / «✅».**

DOM-probe / computed-style / window-globals readback — это **дополнительная** проверка, **не замена** визуального осмотра. Можно сравнить с тем, как QA-инженер тестирует UI — он смотрит на экран, не на DOM-tree.

#### Как именно (минимальная процедура)

В отчёте таска для каждого важного скриншота обязательна **визуальная аннотация** в формате:

```
03_rostov_sdek.png:
  - выбран radio «Доставка СДЭК до ПВЗ» (красная рамка, цена 360 ₽)
  - под radio виден виджет СДЭК с картой ПВЗ, центрирован на Ростов-на-Дону
  - блоки Я.Доставки и Самовывоза НЕ видны (display:none через CSS-injected)
  - в шапке: иконка геолокации «Ростов-на-Дону»
  → PASS критерий 1 (visibility) + критерий 2 (geo-propagation)
```

Если описание `→ FAIL` — таск НЕ закрыт, фикс продолжается. Если агент не может описать (например image-recognition недоступен) — таск НЕ закрыт, нужен ручной осмотр пользователем.

#### Запрещённые анти-паттерны

1. **«Скрин снят, файл существует — значит OK»** — нет. Существование файла = функция `await page.screenshot()` отработала. О содержимом ничего не говорит.

2. **«DOM-probe вернул `display: block` — значит видно»** — нет. Между computed style и реальным rendered viewport есть много слоёв (z-index, overflow:hidden родителя, opacity:0, transform: translateY(-100%), lazy-load карт, MutationObserver задержки). Я.Доставка-widget на скрине заказчицы имел `display:block` И при этом показывал **Ульяновск** вместо <CITY> — потому что внутренний фолбэк виджета игнорировал наш `params.city`.

3. **«Window-global config содержит правильное значение — значит виджет использует»** — нет. Виджеты сторонних SDK (widget-pvz.delivery.example, widget.courier.example) имеют **внутреннюю логику fallback'ов**, кеширование, lazy-init. Установить `window.YANDEX_DELIVERY_DEFAULT_CITY = '<CITY>'` ≠ виджет покажет <CITY>. Нужно открыть скрин и убедиться визуально.

   **Дополнительный анти-паттерн (projectb FIX3 verify, 2026-05-21):** probe засчитал `pass_vis: true` потому что `sdekWChildCount: 1` (контейнер имел дочерний `<iframe>`), но визуально виджет был **пустой белый прямоугольник** — iframe был, но не успел проинициализироваться. **DOM-children-count ≠ rendered viewport.** Минимальные доп. проверки если уж используешь probe: `getBoundingClientRect().height > 100` И `iframe.contentDocument.readyState === 'complete'` И визуальный осмотр скрина. Probe — supplemental, не primary.

4. **«Тестировал в desktop viewport, выглядело хорошо»** — нет. Если заказчик/конечный пользователь смотрит на mobile (как в projectb кейсе — заказчица на iPhone), тесты в desktop viewport (1280×900) не валидируют реальный UX. Mobile viewport (например 375×812 iPhone 13 mini) ОБЯЗАТЕЛЕН в матрице кейсов.

5. **«Сделал N скринов, посмотрел только первые 2-3, остальные = OK по pattern'у»** — нет. Каждый скрин в матрице кейсов — это **отдельный тест**, и каждый должен быть осмотрен. Если есть 12 кейсов — описать 12 наблюдений.

6. **🔴 Скриншоты `puppeteer.screenshot({fullPage: true})` БЕЗ resize'a — крашат Read tool.** Claude API имеет hard-лимит **2000px по длинной стороне** на изображение в multi-image conversation. Mobile-fullPage скрины (375×N где N — высота всей прокрученной страницы 3000-5000px) превышают этот лимит **систематически**. Симптом: после нескольких Read'ов агент получает `"An image in the conversation exceeds the dimension limit for many-image requests (2000px). Start a new session with fewer images."` и **умирает на этой turn'е**.

   **Правило (projectb FIX3 cycle, 2026-05-21):** до visual-verification batch'а — **обязательно** прогнать все скрины через resize до max 2000px:
   ```bash
   mkdir -p screens_after/thumbs
   for png in screens_after/*.png; do
     convert "$png" -resize 'x2000>' "screens_after/thumbs/$(basename $png)"
   done
   ```
   Затем `Read` только из `thumbs/`. Альтернатива — `puppeteer.screenshot({fullPage: false, clip: {x:0,y:0,width:375,height:1900}})` с прокруткой и склейкой, но это сложнее.

   Параметр `convert -resize 'x2000>'`:
   - `x2000` — масштаб по высоте до 2000px
   - `>` — флаг «только если уменьшение» (изображения <2000 не трогаются)
   - сохраняет aspect ratio

   Для PNG лучше использовать ImageMagick (`/usr/bin/convert`); если недоступен — `sharp` или `jimp` через node.

#### Что записывать в task.md

В разделе «Как проверить (Acceptance)» каждого таска, где есть UI-составляющая, **явно** прописать:

```markdown
- [ ] Каждый скриншот в `chat/<TASK>_screens_after/` открыт через Read tool и
      визуально описан в `chat/report_<TASK>.md` в формате:
      «<имя_файла>: <что видно>, <что не видно>, → PASS/FAIL по критерию N».
- [ ] Mobile viewport (375×812) включён в матрицу — отдельные скрины
      `<case>_mobile.png` для каждого кейса.
- [ ] Если визуальное описание не соответствует ожидаемому — таск НЕ закрыт,
      фикс продолжается. Никаких «синтетика PASS, визуально потом проверю».
- [ ] Числовые ожидания (тарифы, координаты) проверены *диапазонами*, не «≠ null».
      Пример СДЭК: для Ростов→Москва тариф 600-900 ₽, для Ростов→СПб 700-1000 ₽.
      Если везде получается ОДНА цифра — это сигнал что что-то захардкожено.
```

#### Кто отвечает за визуальный осмотр

- **Sub-агент** — обязательная первая линия. Открывает свои скрины через Read, описывает, ставит PASS/FAIL.
- **Оркестратор** (если есть) — вторая линия. Спот-проверяет 2-3 случайных скрина по отчёту sub-агента, ловит «синтетика-PASS визуально-FAIL».
- **Пользователь** — последняя линия. Если sub-агент и оркестратор пропустили, ловит пользователь — но тогда **таск считается провалом QA**, не успехом.



Таск-агенты в режиме `-p` видят **только** текст таска. Если в нём нет актуального состояния репо/сервиса — агент сам побежит читать, часто с **неполным** или **устаревшим** пониманием (особенно если прогрев кэша git / локальной копии отстаёт).

**Правило:** в лаунчер-скрипте передавать таск-файлу preamble с текущим состоянием. Без этого агент может «увидеть» прошлое состояние и остановиться на ложных блокерах.

**Минимум в preamble:**
```
АКТУАЛЬНОЕ СОСТОЯНИЕ (на момент запуска):
- Текущая ветка main на VPS: <commit hash> <commit subject>
- Последние N коммитов main: <git log --oneline -5>
- Смержены в main (не надо ждать / не надо снова мержить):
  - <branch-A> (commit <hash>)
  - <branch-B> (commit <hash>)
- Активные параллельные агенты сейчас: <список или "нет">
- Broken state (workaround уже применён, не чинить): <если есть>
```

**Пример формирования (bash):**
```bash
PREAMBLE=$(cat <<EOF
АКТУАЛЬНОЕ СОСТОЯНИЕ НА $(date '+%F %T'):
- Ветка main на VPS: $(ssh user@vps "cd /path && git log --oneline -1 main")
- Последние коммиты:
$(ssh user@vps "cd /path && git log --oneline -5 main")
EOF
)
PROMPT="$PREAMBLE

---

$(cat task_<имя>.md)"
claude --dangerously-skip-permissions -p "$PROMPT" > output.log 2>&1
```

**Пример (кейс DarkHaven, 2026-04-24):** catalog-агент, запущенный без preamble, увидел `cart_security` не в main (на момент его чтения git-кэш был устаревший) и остановился на ложном блокере. Перезапуск с preamble «волны 1-3 уже в main, коммиты f1df1f08/f29b76c4/389fa899/2c79fdea/4b20946f» отработал без блокера за 20 мин.

### 6.1 🔴 Ложные блокеры — СТОП только на настоящей красной линии, не на тревоге

Две ошибки симметричны и обе дорого стоят:
- §5/§7: **проламывать** генуинно сломанное/опасное (потеря данных, lockfile, запись в прод) — ПЛОХО.
- Этот раздел: **вставать** на безопасном/обратимом/разрешённом действии из общей тревоги («страшно», «живая система»,
  «лучше на месте», «нужен специалист») — ТОЖЕ ПЛОХО. Это **ложный блокер**: агент пишет `BLOCKED`/`PARTIAL`, таск стоит
  часами/всю ночь, волна не двигается — хотя работа была выполнима.

🔴 **Ложный стоп — это ТОЖЕ недостоверный отчёт.** Принцип «честность важнее зелёного» (§9.8, формат отчёта) режет в ОБЕ
стороны: фальшивый `SUCCESS` И фальшивый `BLOCKED` одинаково врут. `BLOCKED` оправдан ТОЛЬКО реальной внешней преградой,
не настроением.

**Кейс projecta канал-2 (2026-06-28/29):** автономный агент 5× подряд ОТКАЗАЛСЯ загрузить внешнюю обработку `.epf` на «живую
фискальную кассу», ставя `BLOCKED`/«нужно на месте» — хотя действие было доказано безопасным (вход без авто-РМК, обработка
в безопасном режиме `РежимБезОборудования=Истина` железа не касается, очередь инертна, всё обратимо). ~Сутки простоя ушли в
ложный блокер. Снято: переписали преамбулу (доказательства безопасности, §6) + **переклассифицировали** спорный шаг в
РАЗРЕШЕНО, а красную линию сузили до реального фискального чека/оплаты (это и есть то, что законно остаётся заказчику).

#### Как отличить настоящий блокер от ложного

**Настоящий** (СТОП+пинг оправдан):
- Действие пересекает явную красную линию таска (необратимый ущерб проду, потеря данных, реальные деньги/фиск-операция,
  удаление/перезапись чужого).
- Стандартная команда РЕАЛЬНО упала с конкретной ошибкой (`migrate`/`build`/DESIGNER-сборка/`curl` 4xx-5xx) — приведи дословно.
- Доступ/лицензия/канал ГЕНУИННО недоступны (ПРОВЕРЕНО, а не предположено): нет ssh, занят 1С-сеанс, 401/403 и т.п.

**Ложный** (НЕ повод останавливаться — продолжай):
- «Страшно / опасно / живая система / боевая база» БЕЗ конкретного пересечения красной линии.
- «Лучше / надёжнее на месте / нужен специалист» — когда удалённый путь технически доступен и обратим.
- «Возможно небезопасно / вдруг сломается» — гипотетический риск без доказательства.
- Действие ОБРАТИМО (правка на стороне приложения, открытие формы/файла, read-only запрос статуса) — обратимое почти никогда не блокер.
- Преамбула/задача ПРЯМО помечает действие как разрешённое и доказанно-безопасное.

#### 🔴 Нужен реальный выбор оператора — ЖДАТЬ ОТВЕТ БЕСКОНЕЧНО (не таймаутить, не решать за него)

Если шаг ТРЕБУЕТ решения оператора/владельца, которое нельзя безопасно вывести (бизнес-выбор, развилка A/B/C с разными последствиями для учёта/денег/прода) — пинг законен. Но НЕ ставь `PARTIAL`/`BLOCKED` по таймауту опроса и НЕ принимай решение сам: жди ответ **БЕЗ ОГРАНИЧЕНИЯ ПО ВРЕМЕНИ**.
- Опрашивай входящие TG в цикле **БЕСКОНЕЧНО** (не «N итераций → сдаюсь»), держа сессию/стек живыми (keepalive), с редким повторным нудж-пингом (раз в ~5–10 мин: «всё ещё жду ваш ответ, держу сессию»), пока ответ не придёт.
- Bounded-poll = ДВОЙНАЯ ошибка: (1) ложный `PARTIAL` (работа выполнима, просто ждёт ответа); (2) поздний ответ оператора **теряется** (опрос уже закрыт) — оператор отвечает, а агент уже «сдался».
- В `-p` это синхронный бесконечный цикл опроса (jsonl растёт от polling → supervisor НЕ считает столлом; §9.8bis). Выход из цикла — ТОЛЬКО приход ответа (или явная команда оператора «стоп/отмена»).
- **Кейс projectb T-1C-RU-LIVETEST (2026-06-29):** агент дал bounded-poll ~30 мин на выбор A/B/C и «сдался» в `PARTIAL` — а оператор как раз ответил; ответ потерян, заход впустую. Лечение: ожидание ответа оператора — БЕСКОНЕЧНОЕ (это правило).
- ⚠️ Цена и компромисс: на 1-сеансных ресурсах (1С Fresh = 1 сеанс) бесконечное ожидание держит сессию (владелец заблокирован), пока оператор не ответит — это ОСОЗНАННЫЙ выбор оператора (он сам попросил так, 2026-06-29). Нудж-пинги напоминают, что сессия занята; оператор может в любой момент написать «отмена/логаут».

#### Как НЕ плодить ложные блокеры (работа АВТОРА запуска — в таск-файле/преамбуле)

1. **Точная преамбула с ДОКАЗАТЕЛЬСТВАМИ безопасности** (§6). Без неё агент достраивает страх сам. Не «можно открыть форму»,
   а «открытие проверено сегодня: X, Y, Z → безопасно».
2. **Переклассифицируй заранее**: перечисли ЯВНО действия, которые выглядят страшно, но РАЗРЕШЕНЫ, с причиной почему безопасно.
   Прямая фраза: «Эти действия — НЕ блокеры, выполняй их, не пинай на on-site».
3. **Сузь красную линию до конкретики.** Не «сомнение про железо/данные → СТОП» (ловит всё подряд → генератор ложных стопов),
   а перечень точных запретов: «реальный чек/оплата/смена/денежный ящик/правка типовой конфы». Размытый запрет = ложные блокеры.
4. **Defense-in-depth кодом, а не страхом.** Если действие делается безопасным на уровне кода/конфига (флаг «безопасный режим»,
   dry-run, sandbox, read-only) — включи его, и тогда действие РАЗРЕШЕНО без оговорок. Безопасность через невыполнение — худшая.
5. **Anti-stall язык в задаче**: «„страшно / живая система / нужно на месте / сомнение" — НЕ основание для `BLOCKED`/`PARTIAL`.
   СТОП только при пересечении <красной линии> или реальном падении команды с конкретной ошибкой».

#### Баланс — НЕ перегиб в обратную сторону

Это НЕ «игнорируй безопасность и проламывай». §5 (не обходить реально сломанный штатный путь), §7 (state-changing команды
только если явно в таске), §5.5 (визуальная верификация) — ОСТАЮТСЯ в силе. Цель — убрать СТОПы там, где их быть не должно,
а не добавить риск там, где он реален. Сомнение разрешай В СТОРОНУ действия ТОЛЬКО когда действие обратимо/безопасно/разрешено;
на настоящей красной линии — всегда СТОП.

### 7. Команды, меняющие state — только если явно в таск-файле

Команды, которые генерируют/меняют артефакты схемы/зависимостей/инфраструктуры, НЕ должны выполняться агентом «на автомате», если таск-файл не содержит их **явно** с пояснением зачем. К такими командам относятся:

- `makemigrations` / `alembic revision --autogenerate` / `prisma migrate dev` — генерация новых миграций
- `migrate` / `alembic upgrade` / `prisma migrate deploy` — применение миграций к БД
- `npm install <x> --save` / `pip install` / `cargo add` — изменение lockfile'а
- `terraform apply` / `kubectl apply` / `helm upgrade` — апдейт инфры
- `docker push` / `npm publish` / `cargo publish` — релиз артефакта
- Форматтеры и линтеры с `--fix` / `--write` (`prettier -w`, `black .`, `ruff --fix`) в зонах, где они могут задеть код других задач

**Правило:** если таск-файл не описывает явно «сделай X через Y» — агент не должен инициировать такие команды. Если по ходу работы становится ясно, что нужна миграция / смена зависимостей — агент **останавливается и спрашивает**. Это защита от:
- случайной генерации миграции, которая потом не совпадёт с ручной, которую делает другой агент параллельно
- lockfile-конфликтов при параллельных ветках
- случайного `terraform apply` на прод

Для разрешённых команд — разрешать с флагом «только dry-run» (если применимо): `migrate --plan`, `makemigrations --dry-run`, `terraform plan` без `apply`.

### 8. Параллельный запуск агентов — только через «волны» с файловым замком

Запускать несколько агентов одновременно без координации = коллизии в git (одновременный `git checkout`, конфликты merge), в worktree VPS (два агента `cd` в одну и ту же директорию), в миграциях (оба сгенерировали `0030_*.py`).

**Правило «волны»:**
- **Волна** = набор тасков, у которых **нет пересечений по файлам** (проверять явно по зонам в таск-файлах).
- В каждом таск-файле — **секция «Волна и файловый замок»** с полями:
  - номер волны
  - с чем параллельно
  - что блокирует (merge-порядок)
  - списки «разрешено править» / «ЗАПРЕЩЕНО править» с конкретными путями
- Агент **прямо отказывается** редактировать файлы вне списка — даже если так «логичнее».
- Launch-скрипт запускает агентов с интервалом 60 сек (чтобы worktree-операции одного успевали лечь до старта следующего).
- Merge в основную ветку — **последовательный**, **через временный worktree** (не ломает основной worktree, где могут работать другие).

**Пример формирования волны:**

| Таск | Волна | Параллельно с | Зоны файлов | Merge-порядок |
|------|-------|---------------|-------------|---------------|
| cart_security | 1 | ui_profile, hero_video | views.py::cart, pages/product | 1st |
| ui_profile | 1 | cart_security, hero_video | pages/profile, profile.css | 2nd |
| hero_video | 1 | cart_security, ui_profile | pages/home, hero.css | 3rd |
| catalog | 2 | light_theme | views.py::catalog, catalog.js | после волны 1 |
| light_theme | 2 | catalog | base.html, global.css, SiteSettings | после catalog |

Если зоны пересекаются — агенты **не кладутся в одну волну**, идут последовательно.

### 8.5 Polling sub-процесса на удалённом хосте — избегать `pgrep -f` self-match

Когда sub-агент запускает фоновую команду на VPS (ffmpeg, длинный build, миграция) и потом polling-loop ждёт её завершения через `pgrep -f` — `pgrep -f` смотрит **полную командную строку** всех процессов, включая свой собственный родительский bash, у которого в `argv` есть строка-pattern. **Loop никогда не выйдет.**

**Анти-паттерн (DEADLOCK):**
```bash
ssh vps "ffmpeg ... > out.mp4 &"
ssh vps "until ! pgrep -f 'ffmpeg.*out\.mp4' > /dev/null; do sleep 10; done"
# bash, выполняющий этот until-loop, имеет в argv подстроку 'ffmpeg.*out.mp4'.
# pgrep -f её находит → возвращает PID этого же bash → loop вечен.
```

**Кейс 2026-05-16 (T17 hero-video):** sub-агент завис на 2h40m в таком polling'е к VPS — оркестратор не смог сам диагностировать причину, потребовалось внешнее вмешательство.

**Безопасные варианты ожидания фоновой команды на ssh:**

1. **PID-файл** (рекомендую):
   ```bash
   ssh vps "nohup ffmpeg ... > /tmp/f.log 2>&1 < /dev/null & echo \$! > /tmp/ffmpeg.pid"
   ssh vps "while kill -0 \$(cat /tmp/ffmpeg.pid) 2>/dev/null; do sleep 5; done"
   ```

2. **Sentinel-файл от команды:**
   ```bash
   ssh vps "(ffmpeg ... && touch /tmp/done.sentinel) &"
   ssh vps "while [ ! -f /tmp/done.sentinel ]; do sleep 5; done && rm /tmp/done.sentinel"
   ```

3. **Однострочник `wait` в той же ssh-сессии** (foreground в одной команде):
   ```bash
   ssh vps "ffmpeg ... > /tmp/f.log 2>&1 && echo DONE"   # ssh держит TTY до конца
   ```

4. **Если pattern всё-таки нужен** — исключить себя и grep:
   ```bash
   ssh vps "until ! pgrep -fa ffmpeg | grep -v -E 'pgrep|grep|until' | grep -q 'out\.mp4'; do sleep 10; done"
   ```

🔴 **Тот же self-match убивает и при `pkill`/`kill $(pgrep -f …)`, не только в until-loop.** Если хочешь прибить процесс по паттерну, а твоя же команда содержит этот паттерн в argv — `pkill -f '<pat>'` / `for p in $(pgrep -f '<pat>'); do kill $p; done` **убьёт собственный shell** (exit `128+16=144`), и всё после pkill в той же строке НЕ выполнится. Гаси по PID-файлу / tmux-сессии (`kill-session -t =NAME`), а не по паттерну командной строки. Кейс fb14 2026-07-06 (перезапуск сторожа очереди), см. §12.4.

### 8.6 Диагностика «залип ли sub-агент?» — `pstree`, а не `pgrep -P`

Когда оркестратор проверяет «жив ли sub-агент и что он делает», `pgrep -P <pid>` может **врать**: показывает только прямых children. Если sub-агент держит `bash → sshpass → ssh → remote-bash` цепочку — она НЕ всегда отображается как «дети» главного PID-а Claude, потому что внутренние треды (worker threads самого `claude`) тоже показываются и заслоняют картину.

**Анти-паттерн:**
```bash
pgrep -P <SUB_AGENT_PID>
# вернёт только claude-внутренние treads/процессы → выглядит как «нет children»
# но bash → sshpass → ssh цепочка может быть НЕ видна (зависит от структуры)
```

**Правильный диагностический набор:**

```bash
# 1. Полное дерево процессов:
pstree -p <SUB_PID>
# claude(30407)─┬─bash(3378)───sshpass(3398)───ssh(3399)
#               └─{claude}-threads…
# Если в дереве есть bash/sshpass/ssh/curl/rsync — sub-агент висит на I/O.

# 2. Что именно запущено в каждом не-thread-процессе:
for pid in $(pstree -p <SUB_PID> | grep -oP '\(\K\d+' | sort -u); do
    ps -o pid=,args= -p $pid 2>/dev/null | head -c 200
    echo
done

# 3. Открытые файлы / сокеты (поймать ssh-TCP, file-locks):
lsof -p <SUB_PID> 2>/dev/null | grep -E 'TCP|REG|sock' | head

# 4. Чем занят сейчас main-thread (syscall-tracing, 3 сек):
timeout 3 strace -p <SUB_PID> -c -e trace=read,write,recv,send 2>&1 | tail
```

**Кейс 2026-05-16 (T17):** оркестратор написал *«ssh-цепочка убита, sub-агент обрабатывает результат»*, ориентируясь на `pgrep -P 30407` (видел только claude-threads). Реально `pstree -p 30407` показывал живую цепочку `claude → bash → sshpass → ssh` — sub-агент висел на VPS-polling'е (см. §9 выше). Оркестратор ошибся в диагностике, T17 завис на 2h40m до ручного вмешательства.

**Правило для оркестратора:** перед записью статуса «работает / без children / завис» в логах или прогрессе — обязательно `pstree -p <pid>`, не только `pgrep -P`. Если в дереве есть НЕ-thread процессы (bash/ssh/curl/rsync/etc.) — sub-агент в работе или ждёт I/O. Если только claude-threads — реально думает (API turn) или умер. При сомнении — `lsof` + `strace -c` за 3 сек.

### 8.7 Несколько оркестраторов одновременно — guard на общие машинные ресурсы (SOCKS / VNC / 1С-сеанс)

§8 («волны») разводит агентов ВНУТРИ одного прогона по зонам файлов. Но когда на машине крутятся **два независимых долгоживущих оркестратора** (разные проекты, напр. `/work/projectb` и `/work/projectc`), они дерутся не за файлы, а за **машинные синглтоны**:

| Синглтон | Кто держит | Чем грозит коллизия |
|---|---|---|
| **SOCKS-порт 1080** (double-jump 178→109) | `projectb/scripts/socks_tunnel.sh` (дефолт 1080) | `up` делает `pkill -f "D 127.0.0.1:1080"` → убьёт чужой туннель; `release_session.sh` без `--keep-socks` гасит 1080 |
| **VNC :98 / x11vnc 5901 / CDP 9334** | `vnc_1c.sh` И его клон `projectc/orch/scripts/vnc_lk.sh` | оба `up` делают `pkill -f "Xvfb :98"` + chromium → взаимно сносят стек |
| **VNC :97 / 5902 / CDP 9335** | `vnc_admin.sh` | то же для админ-панели |
| **1С Fresh = 1 сеанс** (тариф «Бизнес») | любой залогиненный | второй логин → «There are no free licenses!» |
| **RAM** (≈3-4 Gi available) | chromium ≈0.7-1 Gi каждый | 2 VNC-chromium + N агентов → swap/OOM |

**Правила для оркестратора, который стартует при возможно-живом соседе:**

1. **Свой SOCKS-порт.** Скрипты `socks_tunnel.sh` / `socks_keepalive.sh` / `vnc_admin.sh` / `vnc_1c.sh` параметризованы `SOCKS_PORT` (дефолт 1080). Если 1080 занят (`ss -ltn | grep 1080`) — подними свой на свободном (1082): `export SOCKS_PORT=1082`. 🔴 Чужой туннель/дисплей, который ты НЕ поднимал, — НЕ гасить и НЕ `pkill`-ить.
   - Передача порта в супервизор: `export SOCKS_PORT=1082` в оркестраторе **+** запуск супервизора как `SOCKS_PORT=1082 bash $SUP`. (env-префикс внутри строки `$STACK_UP_CMD` НЕ сработает: `$VAR`, начинающийся с `NAME=val`, bash после развёртки трактует как имя команды, а не assignment-префикс.)
   - 1С-логаут только `SOCKS_PORT=<свой> bash …/release_session.sh --keep-socks` (без `--keep-socks` погасит дефолтный 1080 = чужой).

2. **Guard перед VNC-таском на общем дисплее.** Перед `vnc_1c.sh up` (или любым стеком на общем :98/:97) проверь, не жив ли соседний прогон, и **СТОП с пингом**, а не клоббер:
   ```bash
   # перед T-1C-POSTING-FIX: :98/5901/9334 общий с projectc/vnc_lk.sh
   if tmux ls 2>/dev/null | grep -qi 'orv' || pgrep -f 'vnc_lk' >/dev/null 2>&1; then
     echo "- [ ] T-1C-POSTING-FIX (HELD: сосед держит :98 $(date '+%F %T'))" >> "$PROG"
     $TG "⏸️ T-1C придержан — :98/CDP9334 занят параллельным прогоном. Не клобберю. Resume: перезапусти когда освободится."
     exit 0            # resume-safe: при перезапуске готовые таски пропустятся по report-файлам
   fi
   ```
   Стоп лучше бесконечного ожидания: соседний прогон может зависнуть на часы (а его прогресс — стоять).

3. **Уникальные имена tmux-сессий + PROJECT_TAG.** Дефолтный `SESSION=orchestrator` (см. `orchestrator_watchdog.template.sh`) у двух прогонов СОВПАДЁТ — watchdog соседа будет «оживлять»/relaunch'ить чужую сессию. Имя сессии и тэг pid-файлов — с префиPROJECTAм проекта (`orv_orchestrator`, `email1c_orch`).

4. **RAM:** очередь последовательная + гасить стек между тасками (`vnc_admin.sh down` после DKIM, ДО следующего шага) — чтобы не держать 2 chromium разом. Перед стартом тяжёлого VNC-таска — `free -h` (смотреть **available**, не free) и `uptime`/`nproc`.

**Кейс 2026-06-05 (projectb email+1C vs projectd delivery):** оба прогона делят SOCKS 1080 и 1С-стек :98/5901/9334 (`vnc_lk.sh` = «клон vnc_1c.sh»). Решение: projectb-оркестратор (`chat/email_1c_orchestrator.sh`) поднят на `SOCKS_PORT=1082` (чужой 1080 не тронут), трек A (DKIM на :97 — не пересекается) прошёл параллельно, а `T-1C-POSTING-FIX` за guard'ом ждёт, пока projectd освободит :98. Без guard'а оба `vnc_*.sh up` поубивали бы Xvfb :98 друг друга.

### 8.8 🔴 `tmux -t <name>` делает ПРЕФИКСНЫЙ матч — watcher может «увидеть сам себя»

`tmux has-session -t NAME` (и `kill-session`/`capture-pane -t`) при отсутствии точного совпадения матчит по **префиксу/fnmatch**, а не только точно. Если orchestrator-скрипт в сессии `foo_resume_watch` проверяет «не бежит ли уже мой sub-прогон» через `tmux has-session -t foo_resume`, то `foo_resume` **префикс-матчит `foo_resume_watch` = саму watcher-сессию** → проверка всегда `true` → watcher вечно думает «sub уже бежит», спит и НИКОГДА не запускает sub. Молча: ни ошибки, ни лога (ветка ожидания обычно без `log`).

**Кейс 2026-06-05 (projectb resume-1c watcher):** сессия watcher'а = `email1c_resume_watch`, проверка sub-прогона = `has-session -t email1c_resume` → префикс-матч → 1С-resume не стартовал ~20 мин, в логе тишина после «ФАЗА 2». Диагноз: `pstree -p <watcher>` показал вечный `sleep`, а `tmux has-session -t =email1c_resume` (точный) → НЕТ (фантом).

**Правила:**
1. Для проверки «жива ли КОНКРЕТНАЯ сессия» — **точный матч**: `tmux has-session -t =NAME` (префикс `=` форсит exact). То же для `kill-session -t =NAME`.
2. Имена сессий не должны быть **префиPROJECTAм** друг друга (`x_run` и `x_run_watch` — плохо; `x_run` и `x_watch` — ок).
3. Если orchestrator/watcher молча «спит и ничего не делает» — первым делом `pstree -p <pid>` (на чём висит) и `tmux has-session -t =name` (точный) vs без `=` (префикс): расхождение = эта грабля.

### 8.9 RAM-сторож — OOM-защита при нескольких оркестраторах на одной машине

Дополняет §8.7 (там guard на SOCKS/VNC/1С). **Оперативка — тоже общий машинный ресурс.** Когда параллельно крутятся 2+ оркестратора (или твой + чужой важный процесс), суммарная RAM может оказаться впритык, а пики (несколько claude одновременно в turn'е) проседают резко. Тогда **Linux OOM-killer прибивает СЛУЧАЙНЫЙ процесс** — может убить чужой оркестратор/прод, а не виновника.

**Кейс projecte 2026-06-06:** на машине 5.8Gi, крутились два оркестратора (projecte-сборка + projectc). В норме available ~3.3Gi, но на пиках (по 2 claude на оркестратор в turn'е) свободно падало до ~800Mi. Без защиты ночной спайк на тяжёлом таске (рисование, где агент в цикле дёргает `claude`) мог OOM-нуть чужую работу.

**Решение — RAM-сторож** (`/work/settings/claude/ram_guard.template.sh`): при `MemAvailable` ниже порога он `kill -STOP` **только СВОИ** sub-агент-группы (по `/tmp/<tag>_T*.pid`), отдавая RAM остальным; при восстановлении — `kill -CONT`. Своя сборка лишь притормаживает, ничего не теряя (всё закоммичено/запушено); чужая работа защищена.

Ключевое:
- Останавливаем **sub-агентов**, не orchestrator-claude (он лёгкий, idle-ждёт; `while kill -0 SUB_PID` переживёт паузу — stopped-процесс жив для `kill -0`).
- **Гистерезис** (PAUSE_KB < RESUME_KB), чтоб не флапать.
- `kill -STOP -- -PGID` по **группе** (runner запущен через `setsid` → PID в pid-файле = PGID; пауза накрывает runner + его claude + внутренних subagent'ов).
- Запуск — **tmux-loop каждые ~20с** (cron'а мало: RAM скачет быстрее минуты):
  ```bash
  tmux new-session -d -s <tag>_ram_guard \
    "bash -c 'while true; do /work/<project_dir>/chat/ram_guard.sh; sleep 20; done'"
  ```
- Снять после финала сборки: `tmux kill-session -t <tag>_ram_guard`.
- Приоритет отдаём «чужому» (важному) — пауза всегда на СВОЕЙ стороне, по своим pid-файлам; чужие процессы не трогаем вообще.

#### 8.9.1 ГЛОБАЛЬНЫЙ RAM-сторож — когда ВСЕ потребители твои (нет чужого соседа)

Per-project сторож (выше) рассчитан на сценарий «мой прогон + ЧУЖОЙ важный процесс»: он душит только свои sub-агенты, отдавая RAM соседу, чужое не трогает. **Но если на машине несколько ТВОИХ нагрузок** (два своих оркестратора + `omx`/oh-my-codex + chromium-стеки), чужого соседа нет, и эта логика оставляет дыру: per-project сторож одного проекта не видит агентов другого проекта и не видит `omx`.

**Кейс 2026-06-20 (фриз):** projectb projectg + projecta T0-ADMIN + omx + 2 chromium в 6Gi → `MemAvailable` упал до ~113Mi → swap-thrash → вся WSL колом (под thrash kernel OOM-killer не успевает). Старый сторож душил только projectb; projecta и omx добили память. Вдобавок projecta-агент завис навечно (старый supervisor без таймаута на «jsonl не появился») и держал RAM зомби.

**Решение — `/work/settings/claude/global_ram_guard.sh`** (machine-wide, НЕ per-project):
- Видит ВСЕ свои тяжёлые процессы: `claude`-агенты(agentuser) с `cwd` под `/work/*` + `omx` (по `pgrep -f 'oh-my-codex|dist/cli/omx'`).
- Приоритет жертв: **omx замораживаем ПЕРВЫМ** (Codex, без супервизора — пауза безопасна), активный sub-агент оркестратора — пауза ТОЛЬКО в аварии (`<350Mi` ≥2 тиков) и НЕ дольше `MAX_PRIMARY_PAUSE=180с` (иначе сработает stall-killer супервизора).
- Гистерезис: pause `<700Mi` (omx) / crit `<350Mi` (агент) / resume всё `>1100Mi`.
- Пишет флаг `/tmp/ram_paused`, пока держит агента в SIGSTOP → **супервизоры обязаны его проверять** и не считать тишину jsonl столлом (см. §12.4; реализовано в `single_agent_supervisor.template.sh` и `projecta/orch/supervisor_admin.sh`).

**Запуск (от ROOT, один на всю машину, до/вместо per-project сторожей):**
```bash
tmux new-session -d -s global_ram_guard \
  "bash -c 'while true; do bash /work/settings/claude/global_ram_guard.sh; sleep 15; done'"
# проверка: tmux ls | grep global_ram_guard ; tail /work/settings/global_ram_guard.log
# (лог ПУСТ при здоровой RAM — пишет только при паузах/давлении)
# снять: tmux kill-session -t global_ram_guard
```
Плюс `sysctl -w vm.swappiness=10` (+ `/etc/sysctl.d/99-swappiness.conf`) — против thrash.

**Полный «эстафетный» запуск двух оркестраторов на 6Gi (НЕ параллелить — §12):**
```bash
sysctl -w vm.swappiness=10
# 1. глобальный сторож (один на всех)
tmux new-session -d -s global_ram_guard "bash -c 'while true; do bash /work/settings/claude/global_ram_guard.sh; sleep 15; done'"
# 2. ПЕРВЫЙ оркестратор (напр. projecta) — его стек + supervisor
tmux new-session -d -s projecta_stack_keeper "bash /work/projecta/orch/stack_keeper.sh"
tmux new-session -d -s projecta_admin_sup -c /work/projecta "bash /work/projecta/orch/supervisor_admin.sh"
# 3. ОЧЕРЕДЬ: сторож ждёт смерти projecta_admin_sup, гасит :99-стек, RAM-гейт, запускает ВТОРОЙ (projectb)
tmux new-session -d -s projectb_qwait "bash /work/projectb/chat/queue_projectb_after_projecta.sh"
```
Глобальный сторож переживает всю эстафету (видит агентов обоих проектов по очереди); per-project `<tag>_ram_guard` при этом НЕ нужны.

#### 8.9.3 Кто поднимает то, что сторож убил (RAM-aware restart, 12.08.2026)

Сторож умеет убивать, но не умеет воскрешать. Раньше цепочка восстановления была дырявой в двух местах.

| Что убили | Кто поднимает | Было | Стало |
|---|---|---|---|
| агента (claude в REPL) | супервизор | respawn МГНОВЕННО, без взгляда на память | `wait_for_ram` перед каждым `launch_agent` |
| супервизора | оркестратор | таск возвращался в очередь, старт под гейтом `ram_ok` | без изменений (это и так правильно) |
| сам оркестратор | НИКТО | очередь стояла до человека | `orchestrator_keeper.template.sh` |

**RAM-гейт в супервизоре** (`claude/claude_supervisor.template.sh`): перед запуском агента ждём,
пока `MemAvailable >= RAM_RESPAWN_MIN_KB` (по умолчанию 1.1 Gi) И снят флаг `/tmp/ram_paused`.
Память есть — стартуем сразу, ничего не замедляя. Памяти нет — ждём тиками по 15 с, потолок
`RAM_WAIT_MAX` (по умолчанию 45 мин), после чего стартуем всё равно и пингуем в TG. Смысл: убийство
сторожем — не вина агента, и мгновенный respawn в тот же дефицит просто жжёт квоту `MAX_RESPAWN`
и уводит здоровый таск в карантин.

**Keeper очереди** (`claude/orchestrator_keeper.template.sh`, запускать от root):
```bash
tmux new-session -d -s <proj>_keeper \
  "PROJECT_DIR=/work/<project> SESSION=<proj>_orch \
   RUNNER=/work/<project>/orch/_run_orch.sh \
   NOTIFY_CMD='python3 /work/tg/bot.py send <chat_id>' \
   bash /work/settings/claude/orchestrator_keeper.template.sh"
```
Раз в минуту проверяет tmux-сессию оркестратора и, если её нет, поднимает — но только когда
`MemAvailable >= MIN_KB` (по умолчанию 1.2 Gi) и снят флаг паузы; иначе ждёт и пишет в TG
(не чаще раза в 30 мин). Перезапуск оркестратора безопасен для работающих тасков: `start_task`
идемпотентен и живые сессии супервизоров пропускает.

🔴 Порог keeper'а выше, чем `RAM_MIN_KB` оркестратора (0.9 Gi), а тот выше нуля: лестница
специально такая, чтобы восстановление шло сверху вниз и не толкало машину обратно в дефицит.


### 9. Долгоживущий оркестратор через tmux

Когда нужен **оркестратор** (агент, который запускает sub-агентов волнами, ждёт их, читает отчёты, решает что дальше) — `claude -p` НЕ подходит: print-режим завершается сразу после ответа. «Я вернусь через 25 минут» — фикция, процесс уже мёртв.

**Решение:** интерактивный `claude --dangerously-skip-permissions` (без `-p`) в **detached tmux-сессии** + cron-watchdog как страховка.

> ⚠️ **Запуск без watchdog запрещён.** Tmux-сессия умирает при первой длительной API-яме (см. §9.3, кейс DH-balance 2026-05-11). Полная процедура: §9.1 launcher → §9.3 watchdog (cron + bash-loop) → §9.7 verify. **Пропускать §9.3 нельзя** — без watchdog'а одна API-яма и весь оркестратор мёртв.

#### 9.1 Запуск оркестратора в tmux (launcher-скрипт)

```bash
#!/bin/bash
# /tmp/launch_orchestrator_tmux.sh
set -e
SESSION=orchestrator
PROMPT_FILE=/work/<проект>/chat/orchestrator_resume_prompt.md

# Защита от повторного запуска
if runuser -u agentuser -- tmux has-session -t $SESSION 2>/dev/null; then
  echo "tmux session '$SESSION' уже существует"
  exit 1
fi

# Detached tmux от agentuser с bash внутри
runuser -u agentuser -- tmux new-session -d -s $SESSION -c /work/<проект> \
  "env -i HOME=/home/agentuser \
        PATH=/home/agentuser/.local/bin:/home/agentuser/.cargo/bin:/usr/local/bin:/usr/bin:/bin \
        SHELL=/bin/bash TERM=xterm-256color bash -i"

sleep 2  # ждём bash init

# Стартуем claude в интерактиве (без -p)
runuser -u agentuser -- tmux send-keys -t $SESSION \
  "claude --dangerously-skip-permissions" Enter

# ⚠️ Trust-folder prompt при первом запуске в новой папке:
# claude показывает «Quick safety check: 1. Yes 2. No». Если просто sleep 20
# и сразу paste — paste уйдёт В МЕНЮ trust prompt'а, будет проигнорирован.
# Шлём Enter после короткой паузы — это принимает default «Yes» (опция 1).
# Если папке уже доверяли раньше — Enter будет no-op (главный prompt не съест
# пустую строку через send-keys без Enter после неё).
sleep 5
runuser -u agentuser -- tmux send-keys -t $SESSION Enter

sleep 20  # claude инициализируется (system prompt, MCP и т.п.)

# Загружаем prompt-файл через paste-buffer (load+paste), потом Enter
runuser -u agentuser -- tmux load-buffer -t $SESSION -b orch_init "$PROMPT_FILE"
runuser -u agentuser -- tmux paste-buffer -t $SESSION -b orch_init
sleep 1
runuser -u agentuser -- tmux send-keys -t $SESSION Enter

# Sanity check: убедись что промпт реально ушёл (capture-pane должен показать
# фрагмент из PROMPT_FILE). Если на экране всё ещё «Quick safety check» —
# trust-prompt не приняли, перезапусти.
sleep 3
if runuser -u agentuser -- tmux capture-pane -t $SESSION -p | grep -q "Quick safety check\|Yes, I trust"; then
  echo "⚠️ FATAL: trust-prompt не принят, паста ушла в меню. Прибей session и перезапусти."
  exit 1
fi

echo "Запущен в tmux '$SESSION'."
echo "Attach: runuser -u agentuser -- tmux attach -t $SESSION"
echo "Detach: Ctrl-b d"
echo ""
echo "⚠️ СЛЕДУЮЩИЙ ШАГ — поставить watchdog в крон (§9.3). Без него запуск НЕ завершён."
```

**Почему именно так:**
- `runuser -u agentuser -- tmux ...` — tmux-сервер от agentuser (свой socket `/tmp/tmux-1000`), не пересекается с root
- `env -i + PATH=...` — те же правила что в §3 (чистое окружение)
- `bash -i` внутри tmux — оболочка с TTY (claude требует TTY, без `-p`)
- `load-buffer + paste-buffer` — надёжнее чем `send-keys "<длинный текст>"` (избегаем эскейпинга многострочного промпта)
- Промпт сохраняем в `.md`-файл — потом можно перезапустить с тем же файлом
- **Trust-Enter после sleep 5** — обязательно. Без него первый запуск в новой папке тихо ломается (paste уходит в trust-меню). Проверено на кейсе projecth 2026-05-17.
- **Sanity-check capture-pane** — ловит ситуацию когда trust-prompt не принят и пользователь думает что всё ОК (но claude висит в меню, sub-agents никогда не появятся).

#### 9.2 Промпт оркестратора — что обязательно

```markdown
## ЖИЗНЕННЫЙ ЦИКЛ
Ты НЕ выходишь пока не выполнены ВСЕ N тасков.
Никаких «scheduled for later», только активный sleep+check loop в Bash:

while ps -p <PID> > /dev/null 2>&1; do
  sleep 120   # < 5 мин — держим prompt cache тёплым
done
# теперь читаем output_*.log и report_*.md

## ДИАГНОСТИКА «sub-агент жив / работает / завис»

Перед записью статуса (в pane, progress.md, watchdog log) — **обязательно** `pstree -p <SUB_PID>`,
не только `pgrep -P` (см. §8.6). Внутренние claude-threads видны как процессы и скрывают bash/ssh-цепочку.

- Дерево содержит bash/sshpass/ssh/curl/rsync/ffmpeg — sub-агент **жив, ждёт I/O** (нормально).
- Дерево пустое кроме claude-threads — sub-агент думает (API turn) ИЛИ умер. Проверь `lsof -p` + `strace -c -p` 3 сек.
- Pgrep на удалённом VPS с `-f 'pattern'` — может match сам себя (см. §8.5), DEADLOCK.

Если sub-агент >45 мин с log = 0 байт И `pstree` показывает живой ssh/sshpass к VPS — посмотри
**что висит на удалённой стороне**: `ssh vps "ps -ef | grep -E '<pattern>'"` — типично polling-loop с pgrep self-match.

## КРИТЕРИИ «таск ✅»
1. ps -p <PID> пуст
2. output_<имя>.log не пустой
3. report_<имя>_*.md существует
4. в report — «merged into main» с commit-хешем
5. на VPS git log main подтверждает merge

## 🔴 PROGRESS.MD — ДИСЦИПЛИНА (резюм-безопасность)

`/work/<проект>/chat/orchestrator_progress.md` — единственный источник правды
для resume после падения. Ты ОБЯЗАН:

1. **Сразу после факта merge** (≥3 из 5 критериев ✅) — записать `[x]` в
   progress.md строкой с commit-хешем и кратким резюме. ДО любых других
   действий. Никаких «потом запишу, сначала запущу следующее».

2. **Запрет: запуск sub-агента следующей волны БЕЗ записи** о предыдущей в
   progress.md. Если предыдущая ✅, но не записана — сначала Edit
   progress.md, ПОТОМ spawn. Иначе при падении в промежутке resume
   запустит уже-готовый таск повторно.

3. **TODO-tree в твоей памяти ≠ progress.md.** В pane ты видишь ✔ DH-X —
   это в твоей оперативной памяти, она умрёт вместе с tmux. На диске
   progress.md — то что переживёт падение. Синхронизируй ОДНО с ДРУГИМ
   немедленно.

4. **Watchdog считает прогресс по progress.md.** `grep -c '^- \[x\]'` —
   если ты не записал, watchdog скажет «7/15» когда реально 8/15. Это не
   косметика — это сигнал тебе самому и пользователю.

5. **Перед записью прочитай файл** (`Read` tool) и используй `Edit` с
   уникальным контекстом — НЕ перезаписывай файл целиком, иначе можешь
   стереть параллельную правку которую делает другой инструмент.

**Кейс DH-balance 2026-05-11 09:00:** DH-7 завершился в 08:22, оркестратор
увидел `✔ DH-7` в pane, запустил A + B-1 + DH-FIX, но progress.md не
обновил — watchdog рапортовал `7/15` вместо `8/15`. Если бы оркестратор

## ТОЧКА ВЫХОДА
Единственная — все N тасков ✅ → финальный пинг → exit.
Любые блокеры → пинг пользователю через Telegram bot → продолжать ждать.

## НЕЗАПЛАНИРОВАННЫЕ ТАСКИ

Если sub-агент в отчёте прямо рекомендует «запустить отдельный fix-таск»
для локальной проблемы (1-2 файла, не системная) — ты МОЖЕШЬ запустить
такой таск без согласования с пользователем, но ОБЯЗАН:

1. Сразу пингнуть пользователя: «🔧 запускаю незапланированный <имя>: <причина из отчёта>»
2. Добавить строку в progress.md в раздел «Незапланированные» (создай если нет)
3. Считать его частью общего счётчика готовности (если запустил X, то цель = N+X)

Если рекомендация системная (миграция БД, lockfile, инфра) — НЕ запускай
сам, только пинг + жди решения пользователя.

РАСШИРЕНИЕ (2026-07-11) — оркестратор авторствует таск по СВОЕМУ диагнозу:
случай выше реактивный (саб-агент сам попросил fix). Более сильная схема — оркестратор

HOW_TO_LAUNCH_AGENTS.md §«Автономный оркестратор: сам пишет таск-файлы».
```

#### 9.3 Главный риск — API timeout убивает всю сессию

Если Anthropic API timeout'ит ≥10 ретраев подряд (бывает при rate-limit или backend-blip):
- `claude` CLI выходит с синтетическим `"Request timed out"` (видно в `~/.claude/projects/-*/<session>.jsonl` как `isApiErrorMessage:true`)
- bash в tmux завершается (claude был foreground)
- tmux-окно умирает → `tmux ls` показывает «no server running»
- **Правило «не выходи» в промпте НЕ помогает** — выходит сам CLI-бинарь, а не модель

Sub-агенты в `-p` режиме страдают тем же. В кейсе DH-balance (2026-05-11 ~04:00 MSK) одна API-яма убила оркестратор + DH-7 одновременно: оркестратор после 10 ретраев, DH-7 — на первом запросе (только что в очереди).

#### 9.3bis — 5-часовой / session-лимит Claude (НЕ путать с API-timeout)

Отдельный от §9.3 случай: упёрлись в **квоту** (5-часовое окно / session limit). Тогда `claude -p` НЕ ретраит, а **сразу выходит** с сообщением в output-логе, например:
- `You've hit your session limit · resets 7:30pm (Africa/Casablanca)`
- `usage limit reached`, `rate limit`, `429`, `overloaded`, `please try again`.

Правильная реакция супервизора: **НЕ тратить respawn**, а **ждать сброса квоты и сам перезапуститься** — циклом, пока квота не вернётся. Реализовано в `single_agent_supervisor.template.sh` (функция `handle_rate_limit`, `RL_RE`, `RL_WAIT`); вызывается в КАЖДОЙ ветке (death / stall / no-jsonl) ПЕРЕД `respawn_count++`.

🔴 **Кейс PROJECTA 2026-06-30 (почему добавлено в шаблон):** агент PROJECTA упёрся в session-лимит с текстом `You've hit your session limit · resets 7:30pm`. Старый `RL_RE` ловил `usage limit`/`5-hour`/`resets at`, но **не** `session limit` / `resets 7:30pm` → супервизор счёл это обычной смертью, сделал respawn, который тут же снова упёрся в лимит → `FATAL: launch не дал живого PID` → оркестратор умер на ~2.5ч (до сброса). Два урока, оба теперь в шаблоне:
1. **`RL_RE` должен покрывать формат `session limit` / `hit your … limit` / `resets <время>pm`** (не только `usage limit`/`resets at`).
2. **Ожидание — циклом, а не один `RL_WAIT`:** сброс может быть через несколько часов; `handle_rate_limit` крутит `wait RL_WAIT → relaunch` до возврата квоты (cap 24× ≈ 10ч), иначе один 25-мин таймаут не покрывает многочасовой сброс.

Любой кастомный супервизор (per-project) ОБЯЗАН содержать ту же RL-логику — сверяться с актуальным `single_agent_supervisor.template.sh`.

**Обязательный шаг при запуске оркестратора — cron-watchdog (отдельный процесс от root, не зависит от claude):**

> 📄 Готовый шаблон лежит в `/work/settings/claude/orchestrator_watchdog.template.sh` (версия 2026-05-23). Скопируй в `/work/<проект>/chat/orchestrator_watchdog.sh`, поправь блок «НАСТРОЙКИ» (`PROJECT_DIR`, `ORCHESTRATOR_USER`, `TOTAL_TASKS`, `JSONL_DIR`, `CHAT_ID`), `chmod +x`.

Шаблон проверяет (в порядке выполнения тика):

1. **`progress.md` существует** — иначе оркестратор ещё не запускался, exit 0.
2. **Все таски ✅** (`[x]`, не `[ ]` и не `[~]`) → снимает себя из cron + kill B-loop + удаляет state-dir.
3. **Tmux-сессия жива** → если нет, relaunch через launcher + TG-пинг `♻️`.
4. **Claude-процесс внутри tmux жив** → если нет, kill session + relaunch + TG-пинг.
5. **API-ретраи в jsonl** (новый сценарий — версия 2026-05-23): сканирует `~agentuser/.claude/projects/-work-<проект>/*.jsonl` за последние `JSONL_LOOKBACK_HOURS` (default 6ч) на `"isApiErrorMessage":true`. При росте счётчика — TG-пинг `WARN`. Cooldown 30 мин чтобы не спамить.
6. **Pstree-based zombie detection** (новый — версия 2026-05-23): для каждого claude-PID под `$ORCHESTRATOR_USER` смотрит `pstree -p`. Если у ВСЕХ claude-процессов только `{claude}`-threads (нет bash/ssh/curl/sshpass/ffmpeg-children) — счётчик `zombie_ticks++`. Когда ≥`ZOMBIE_TICK_LIMIT` тиков (default 12 × 5 мин = 60 мин) — TG-пинг `ALERT` один раз за инцидент. Сбрасывается при обнаружении активности.
7. **Heartbeat в лог** — `progress: N✓/M~/TOTAL, api_retries=X, zombie_ticks=Y`.

State между тиками хранится в `/tmp/orch_watchdog_state/` (api-counter, zombie-counter, last-alert-ts). Удаляется при финале (шаг 2).

**Что покрывает / не покрывает:**

| Сценарий | Покрытие |
|---|---|
| API-яма убивает CLI (≥10 ретраев) → tmux dead | ✅ шаг 3+4 — relaunch |
| API-ретраи без смерти CLI (промежуточные ошибки) | ✅ шаг 5 — TG-алерт |
| Sub-агент завис в polling-deadlock (см. §8.5) | ⚠️ частично — шаг 6 если нет non-thread-children >60 мин |
| Anthropic backend down 30+ мин | ✅ скатывается в шаг 3+4 |
| Orchestrator zombie без активности и без ретраев | ✅ шаг 6 |
| WSL ↔ Anthropic network partition | ✅ скатывается в шаг 3+4 |
| Sub-агент честно работает долго (>60 мин на одной API-turn) | ⚠️ может дать false-positive — `ZOMBIE_TICK_LIMIT` подкрути под проект |

Полный скрипт — в файле шаблона (~180 строк). Краткий каркас без новых проверок (для понимания базовой логики):

**Бекап-watchdog (B) — bash-loop в отдельной tmux-сессии** (страховка на случай гибели cron-демона):

```bash
# От root, в отдельной tmux-сессии 'orch_watchdog_loop'
tmux new-session -d -s orch_watchdog_loop -c /work/<проект> \
  "bash -c 'while true; do /work/<проект>/chat/orchestrator_watchdog.sh; sleep 300; done'"

# Проверка
tmux list-sessions    # должна быть orch_watchdog_loop
tmux capture-pane -t orch_watchdog_loop -p | tail -10

# Снять после финала (вручную, если шаблон watchdog'а ещё не самоубивает B-loop):
tmux kill-session -t orch_watchdog_loop
```

A + B вместе — primary (cron) и secondary (bash-loop). На старте могут гоняться (оба ткнутся в launcher одновременно), это безопасно — launcher идемпотентен через `tmux has-session`, лишняя попытка завершается с `set -e exit 1` (без ошибки в нашей версии — exit 0 + warning), а вторая проходит.

> ⚠️ **Порядок установки watchdog'ов vs manual launcher (кейс projecth 2026-05-17):** если ты сначала ставишь B-watchdog (tmux bash-loop), его первый тик отработает **через 0 сек** — увидит «orchestrator DEAD» и **сам** вызовет `launch_orchestrator_tmux.sh`. Manual launcher после этого ответит «session уже есть — skip».
>
> Это **нормально и безопасно** (launcher идемпотентен через `tmux has-session`), но в логе watchdog'а будет видна запись «Relaunching...». **Если хочешь чистый старт без relaunch-сообщения** — порядок: 1) launcher вручную → 2) cron-watchdog → 3) B-watchdog. Если порядок неважен — ставь watchdog'и любым порядком, итог тот же.

> ⚠️ **B-watchdog после финала всех тасков (кейс projecth 2026-05-17):** A-watchdog (cron) **сам себя удаляет** из crontab при условии `! grep '^- [ ]'` (см. скрипт). **B-watchdog (bash-loop) не имеет встроенного self-kill** в шаблоне до версии 2026-05-18 — без правки он будет тикать каждые 5 мин с записью «all tasks done — uninstalling from cron» в лог бесконечно.
>
> **Лечение** — в watchdog.sh добавлен B-loop self-kill (шаблон 2026-05-18+ это делает автоматически):
> ```bash
> # После «all tasks done — uninstalling from cron»:
> if tmux has-session -t orch_watchdog_loop 2>/dev/null; then
>   echo "[$(date '+%F %T')] B-loop self-kill: tmux kill-session orch_watchdog_loop"
>   tmux kill-session -t orch_watchdog_loop 2>/dev/null
> fi
> ```
> Старые шаблоны (без self-kill) — снимай вручную: `tmux kill-session -t orch_watchdog_loop`.

> ⚠️ **Грабли с TMUX env** (кейс DH-balance 2026-05-11): когда watchdog запущен из tmux-сессии (B-вариант), он наследует env-переменную `TMUX=/tmp/tmux-0/default,...`. Внутри `runuser -u agentuser -- tmux has-session` runuser сохраняет эту env → tmux пытается коннектиться к root-сокету как agentuser → `Permission denied` → ложно-позитив «session DEAD» → бесполезный рестарт каждые 5 минут.
>
> **Лечение** — в начале watchdog'а `unset TMUX TMUX_PANE TERM` (уже в скрипте выше). После фикса B-watchdog рапортует `alive (PID …), progress: N/15 tasks done` корректно. Cron-watchdog (A) от этой бажки не страдает (cron вызывает скрипт без TMUX env).

#### 9.4 Resume-промпт — что туда писать

При рестарте оркестратор должен **сразу понять, что уже сделано**, чтобы не запустить DH-1 второй раз. Минимум в `orchestrator_resume_prompt.md`:

1. **Текущий main commit** (один `ssh user@vps "git log -1 --oneline main"`)
2. **Список уже готовых тасков** с commit-хешами merge'ей (или ссылка на `orchestrator_progress.md`)
3. **Следующая волна** — что запускать
4. **Запрет** перезапускать готовые таски
5. **Жизненный цикл** (см. §9.2)
6. **Технические правила:**
   - НЕ `runuser -u agentuser` внутри tmux (ты УЖЕ agentuser — PAM не пустит вложенный runuser)
   - Спавн sub-агентов: `setsid env -i ... bash -c "... claude -p \"\$(cat /tmp/prompt_<имя>.txt)\" > output.log 2>&1" </dev/null >/dev/null 2>&1 &`
   - Большие промпты (>80КБ) — в `/tmp/prompt_*.txt`, ссылка через `$(cat ...)`

#### 9.5 Мониторинг tmux-оркестратора

```bash
# Что сейчас на экране оркестратора (последние 40 строк)
runuser -u agentuser -- tmux capture-pane -t orchestrator -p | tail -40

# Сессии живы?
runuser -u agentuser -- tmux list-sessions

# Прицепиться (Ctrl-b d чтобы отцепиться)
runuser -u agentuser -- tmux attach -t orchestrator

# Состояние тасков
cat /work/<проект>/chat/orchestrator_progress.md | grep -E '^- \['

# Что пошло не так (если API упал)
ls -lt ~agentuser/.claude/projects/-work-<проект>/*.jsonl | head -3
tail -3 ~agentuser/.claude/projects/-work-<проект>/<последний>.jsonl | python3 -m json.tool | head -50
# смотри isApiErrorMessage:true и retryAttempt — diagnostic API-падений
```

#### 9.6 Когда tmux-оркестратор НЕ нужен

- Один таск без зависимостей → обычный `claude -p` **+ обязательно watchdog (§9.8)**
- 2-3 таска одной волны → bash-launcher с `wait` (см. §2) **+ один общий watchdog или по одному на агента**
- Серия из 4+ тасков с зависимостями между волнами → **только tmux + watchdog (§9.3)**

> ⚠️ **Watchdog нужен ВСЕГДА, не только для оркестратора.** Одиночный `claude -p` страдает от API-таймаутов так же — после ≥10 ретраев claude CLI умирает, sub-агент тихо вылетает с пустым логом, юзер узнаёт об этом только когда зайдёт проверить. Watchdog ловит ретраи в `~/.claude/projects/-*/<session>.jsonl` (поле `isApiErrorMessage:true`) и шлёт TG-пинг сразу, не давая упустить проблему. См. §9.8 — готовый шаблон для одиночного агента.

#### 9.7 Чеклист запуска оркестратора (по шагам)

```bash
# 0. Проверки окружения
service cron status                                              # WSL: должно быть "running", иначе → start
ls /work/<проект>/chat/orchestrator_resume_prompt.md             # промпт с актуальным состоянием
ls /work/<проект>/chat/orchestrator_progress.md                  # таблица «таск → статус»
ls /tmp/launch_orchestrator_tmux.sh /usr/local/bin/orchestrator_watchdog.sh   # оба исполняемые

# 1. Resume-промпт актуален? — проверить что «уже сделано» отражает реальный main
sshpass -p '<vps_pwd>' ssh root@<vps_ip> "su - <prod_user> -c 'cd <repo> && git log -5 --oneline main'"
# Сверить с разделом «✅ Готово N из M» в resume-промпте. Если main опережает — обновить.

# 3. Поднять bash-loop watchdog (B) от root

  "bash -c 'while true; do /usr/local/bin/orchestrator_watchdog.sh; sleep 300; done'"

# 4. Запустить оркестратор (watchdog сам это сделает в течение 5 мин,
#    либо вручную если хочется сразу):
/tmp/launch_orchestrator_tmux.sh

# 5. Проверка через ~40-60 секунд

ps -ef | grep claude | grep agentuser | grep -v session_saver | grep -v grep
#    Признаки «всё ОК»: видим TODO-tree из N пунктов, sub-агент запущен, sleep+check loop
```

**Что снять после финала (все таски ✅):**
```bash
# A-watchdog должен сам уйти из крона по условию (см. скрипт §9.3), проверь:
crontab -l | grep orchestrator_watchdog       # пусто = ОК

# B-watchdog (bash-loop) — шаблон 2026-05-18+ сам себя убивает после финала
# (см. §9.3 правку). Если ставил старый шаблон — снимай вручную:
tmux kill-session -t orch_watchdog_loop       # bash-loop B (если шаблон без self-kill)

# Оркестратор-claude в tmux — НЕ выходит сам, нужно прибить (см. §9.8):
runuser -u agentuser -- tmux kill-session -t orchestrator
```

> ⚠️ **Финальный exit оркестратора — не реальный exit (кейс projecth 2026-05-17).** Промпт §9.2 говорит «exit» как точку выхода, но `claude --dangerously-skip-permissions` без `-p` — это **REPL**. Когда модель напишет «Exit.» в pane, она просто продолжает идти в interactive mode, tmux-сессия остаётся жива. Способы реально завершить:
>
> 1. **Из самой claude через слэш-команду** — научить оркестратор в финале запускать `/exit` в свой pane: `tmux send-keys -t orchestrator '/exit' Enter`. CLI завершится, tmux окно умрёт.
> 2. **Снаружи через kill-session** — `runuser -u agentuser -- tmux kill-session -t orchestrator` (см. выше).
>
> На практике пункт 2 надёжнее — даже если claude по какой-то причине проигнорировал `/exit`, kill-session гарантированно прибивает. Делать оба некритично: первое — для чистоты лога, второе — для гарантии.

#### 9.8 Watchdog для одиночного `claude -p` (без tmux-оркестратора)

API-таймаут убивает одиночный sub-агент так же, как оркестратор (см. §9.3). Без watchdog'а пустой output.log + молчание = единственный сигнал, который замечают только при ручной проверке. **Правило: любой `claude -p` запуск — c watchdog'ом**, даже если это «маленький фикс на 15 минут».

Watchdog шлёт TG-пинг на:
- **API-ретрай** — найден новый `"isApiErrorMessage":true` в `~agentuser/.claude/projects/-work-<проект>/*.jsonl` с прошлого тика (это главная защита — обычно ради этого вся затея).
- **Смерть процесса** — `kill -0 $SUB_PID` упал; в TG идёт хвост лога (последние 1500 байт).
- **Стагнация** — лог не растёт ≥45 мин при живом PID (возможно длинный API-turn или завис).
- **Финал** — sub-агент умер И в логе найден `SUCCESS_MARKER` (обычно `✅ <TASK_ID>`); watchdog рапортует успех и самоубивается.

> 📄 Готовый шаблон: `/work/settings/claude/single_agent_watchdog.template.sh`. Заполнить блок «НАСТРОЙКИ» (TASK_ID, LOG, PID_FILE, JSONL_DIR, SUCCESS_MARKER), скопировать в `/tmp/<TASK_ID>_watchdog.sh`, запустить от root в tmux.

##### 9.8.1 Launcher с PID-capture

В отличие от §3-§4, для watchdog'а нужен **PID самого процесса claude**, не PID `setsid`/`runuser`-обёртки. Решение: в bash-launcher делаем `echo $$ > /tmp/<TASK_ID>.pid` ДО `exec claude` — после `exec` bash-процесс становится claude с тем же PID.

```bash
# /tmp/<TASK_ID>_launch.sh
#!/bin/bash
cd /work/<проект>
echo $$ > /tmp/<TASK_ID>.pid
exec claude --dangerously-skip-permissions -p "$(cat /tmp/<TASK_ID>_prompt.txt)" \
  > /work/<проект>/chat/<TASK_ID>_output.log 2>&1
```

##### 9.8.2 Полная последовательность запуска

```bash
TASK_ID=T-EXAMPLE
PROJECT=projectb

# 0. Pre-flight (см. §11.2, workflow.md проекта)
runuser -u agentuser -- grep -c "\"/work/$PROJECT\"" /home/agentuser/.claude.json   # trust = 1
ss -tlnp | grep 1080                                                       # SOCKS5 жив (если нужен)

# 1. Подготовить prompt-файл (preamble + task), см. §6
cat /tmp/${TASK_ID}_preamble.txt /work/$PROJECT/orchestrator_tasks/${TASK_ID}.md \
  > /tmp/${TASK_ID}_prompt.txt

# 2. Подготовить лог под agentuser
touch /work/$PROJECT/chat/${TASK_ID}_output.log
chown agentuser:agentuser /work/$PROJECT/chat/${TASK_ID}_output.log
chmod 666 /work/$PROJECT/chat/${TASK_ID}_output.log

# 3. Создать launcher с PID-capture (см. §9.9.1)
cat > /tmp/${TASK_ID}_launch.sh << EOF
#!/bin/bash
cd /work/$PROJECT
echo \$\$ > /tmp/${TASK_ID}.pid
exec claude --dangerously-skip-permissions -p "\$(cat /tmp/${TASK_ID}_prompt.txt)" \\
  > /work/$PROJECT/chat/${TASK_ID}_output.log 2>&1
EOF
chmod +x /tmp/${TASK_ID}_launch.sh
chown agentuser:agentuser /tmp/${TASK_ID}_launch.sh
rm -f /tmp/${TASK_ID}.pid

# 4. Запуск sub-агента от agentuser (env -i + setsid + detach, см. §4)
setsid runuser -u agentuser -- env -i \
  HOME=/home/agentuser \
  PATH="/home/agentuser/.local/bin:/home/agentuser/.cargo/bin:/usr/local/bin:/usr/bin:/bin" \
  SHELL=/bin/bash \
  bash /tmp/${TASK_ID}_launch.sh </dev/null >/dev/null 2>&1 &

sleep 4
SUB_PID=$(cat /tmp/${TASK_ID}.pid)
echo "claude PID: $SUB_PID"

# 5. Скопировать шаблон watchdog'а и заполнить НАСТРОЙКИ
cp /work/settings/claude/single_agent_watchdog.template.sh /tmp/${TASK_ID}_watchdog.sh
sed -i "s|T-EXAMPLE|${TASK_ID}|g; s|<проект>|${PROJECT}|g" /tmp/${TASK_ID}_watchdog.sh
chmod +x /tmp/${TASK_ID}_watchdog.sh

# 6. Запустить watchdog от root в tmux (имя сессии = '<TASK_ID_short>_watch')
tmux kill-session -t ${TASK_ID}_watch 2>/dev/null
tmux new-session -d -s ${TASK_ID}_watch -c /work/$PROJECT \
  "bash /tmp/${TASK_ID}_watchdog.sh"

# 7. Проверка через 3 сек
sleep 3
tail -5 /work/$PROJECT/chat/${TASK_ID}_watchdog.log
tmux list-sessions | grep ${TASK_ID}_watch
ps -p $SUB_PID -o pid,etime,stat,cmd
```

##### 9.8.3 Мониторинг и снятие

```bash
# Heartbeat watchdog'а (тик каждые 90с — alive/log-size/retries/silence)
tail -f /work/<проект>/chat/<TASK_ID>_watchdog.log

# Жив ли sub-агент?
ps -p $(cat /tmp/<TASK_ID>.pid) -o pid,etime,stat,cmd

# Output (заполнится в конце для -p режима)
tail -f /work/<проект>/chat/<TASK_ID>_output.log

# Прицепиться к watchdog (Ctrl-b d — отцепиться)
tmux attach -t <TASK_ID>_watch

# Снять вручную (обычно watchdog сам самоубивается на death/finale)
tmux kill-session -t <TASK_ID>_watch
```

##### 9.8.4 Грабли

1. **`grep -c` + `|| echo 0`** — если grep не находит совпадений, он печатает `"0"` и возвращает exit code `1`, затем `|| echo 0` добавляет ещё одну `"0"` → получается `"0\n0"`, и `[ "$x" -gt … ]` падает с `integer expression expected`. Шаблон использует `[ -z "$x" ] && x=0` вместо этого паттерна.
2. **`echo $$` после `exec`** — нельзя, `exec` уже заменил bash на claude. Записывать PID нужно ДО `exec`, тогда `$$` остаётся валидным (после exec PID не меняется).
3. **JSONL_DIR должен соответствовать проекту** — claude-сессии хранятся в `~agentuser/.claude/projects/-work-<проект>/<session-uuid>.jsonl` (слеши в пути конвертируются в дефисы с префиPROJECTAм `-`). Для `/work/projectb` → `/home/agentuser/.claude/projects/-work-projectb/`. Проверь через `ls ~agentuser/.claude/projects/` если не уверен.
4. **`SUCCESS_MARKER` должен совпадать с реальной строкой в выводе** — шаблон ищет финальный «✅ <TASK_ID>» в логе. Если в таск-файле финальный TG-пинг начинается с другого символа — поправь SUCCESS_MARKER, иначе watchdog рапортует «без success-маркера» даже на успешном финале.
5. **`stat` показывает `Sl` для живого claude** — это нормально (sleeping, multi-threaded). `kill -0 $PID` — единственный надёжный тест на «жив».

##### 9.8.5 Когда watchdog НЕ нужен

Очень узкий список:
- Интерактивная сессия (этот REPL, без `-p`) — пользователь сам видит ретраи.
- One-shot puppeteer-скрипт от agentuser (`node script.js`) — нет API к Anthropic, нечему ретраить.
- Команда таска подразумевает <2 мин работы (мелкая правка ОДНОГО файла без рекона) — даже одна API-яма не успеет включиться. Но и тогда дешевле поставить watchdog по привычке, чем потом разбираться.

Везде остальное — watchdog обязателен.

#### 9.8bis Supervisor одиночного агента (watchdog, который САМ перезапускает)

> 📄 Готовый шаблон: `/work/settings/claude/single_agent_supervisor.template.sh` (версия 2026-06-01).

**Зачем, если уже есть watchdog (§9.8).** Watchdog — пассивный наблюдатель: только пингует в TG и сам ничего не перезапускает. Главное — он ловит стагнацию по `output.log`, а в режиме `-p` тот **пуст до самого конца**. Значит при `output.log = 0` watchdog не может отличить здоровую работу от зависания. А самый коварный сбой — это именно **API-turn STALL**: процесс claude жив (`kill -0` проходит), но HTTPS-соединение к Anthropic API повисло без ответа и **не таймаутит само**. `pstree` показывает только `{claude}`-threads (нет bash/ssh/curl-детей), `output.log = 0`, и так может стоять десятками минут. Watchdog максимум пингнёт на 45-й минуте — и всё.

**Что делает supervisor.** Внешний bash-процесс от root, который детектит зависание по **росту JSONL-сессии** (`~agentuser/.claude/projects/-work-<проект>/<uuid>.jsonl` растёт стримингом каждые секунды при живой работе; не растёт N минут = turn завис), и **сам**:
1. убивает зависший агент **по его PID** (grace `TERM`→`KILL`),
2. переподнимает внешний стек, если он нужен и отвалился (VNC/CDP/headless-chromium),
3. **респавнит** агента через тот же launcher (лимит `MAX_RESPAWN`),
4. **выходит при успехе** — когда в `report_<TASK>.md` стоит `STATUS: SUCCESS` (само появление файла = ФИНИШ, не успех; `FAIL/BLOCKED/PARTIAL` → `⚠️` exit 2; нет STATUS → `⚠️` exit 3), или при исчерпании лимита (TG-алерт).

**Когда брать supervisor вместо watchdog:**

| Ситуация | Инструмент |
|---|---|
| Короткий изолированный таск (<10 мин), правка 1-2 файлов | watchdog (§9.8) |
| Длинный таск (десятки минут), где API-turn периодически виснет | **supervisor** |
| Таск с внешним стеком (VNC/CDP/headless), который может отвалиться | **supervisor** (умеет переподнять стек перед respawn) |
| Не хочешь сам сидеть в петле и перезапускать руками | **supervisor** |

**Почему НЕ §9-оркестратор для одного таска.** Полноценный оркестратор (интерактивный `claude` в tmux, §9.1-9.3) сам подвержен тем же API-зависаниям — для одиночного таска это и оверкилл, и не лечит проблему. Supervisor именно потому надёжен, что он **внешний** (обычный bash от root), а не ещё один claude.

**Stall-детект — ключевая идея (НЕ повторять ошибку watchdog'а):**
```bash
# output.log в -p пуст до конца → бесполезен как индикатор живости.
# JSONL растёт стримингом → вот настоящий пульс агента:
J=$(find "$JSONL_DIR" -maxdepth 1 -name '*.jsonl' -newermt "@$LAUNCH_TS" | xargs -r ls -t | head -1)
AGE=$(( $(date +%s) - $(stat -c %Y "$J") ))   # сколько сек jsonl не трогался
[ "$AGE" -ge "$STALL_LIMIT" ] && kill_sub && respawn   # STALL_LIMIT=420 (7 мин)
```

**Запуск (зависимости те же, что у watchdog §9.8.2 — launcher с PID-capture, prompt, лог):**
```bash
TASK=T-EXAMPLE; PROJECT=projectb
cp /work/settings/claude/single_agent_supervisor.template.sh /tmp/${TASK}_supervisor.sh
# заполнить блок НАСТРОЙКИ: TASK, PROJECT, REPORT (+ STATUS_RE: успех по статус-строке, НЕ по факту файла), STACK_*  (или пусто если стек не нужен)
sed -i "s|T-EXAMPLE|${TASK}|g; s|<проект>|${PROJECT}|g" /tmp/${TASK}_supervisor.sh
chmod +x /tmp/${TASK}_supervisor.sh
tmux new-session -d -s ${TASK}_sup -c /work/$PROJECT "bash /tmp/${TASK}_supervisor.sh"
# мониторинг:  tail -f /work/$PROJECT/chat/${TASK}_supervisor.log
# снять:       tmux kill-session -t ${TASK}_sup   (supervisor и сам выходит при success/лимите)
```

> 🔴 **Безопасность (как и у watchdog):** supervisor убивает **только свой `SUB_PID`** из PID-файла. **Никогда** `pkill -f claude` / `pkill -f chrome` — у юзера часто параллельные сессии по другим проектам. Стек поднимать/гасить только через идемпотентный `STACK_UP_CMD` (или точечно по PID).

**Финиш-сигнал — файл, УСПЕХ — СТАТУС-строка ВНУТРИ него (не факт файла).** 🔴 Раньше supervisor слал `✅` и выходил `exit 0` по самому *появлению* `report_<TASK>.md`. Это давало **недостоверные «успехи»**: честный отчёт о провале/блокере — это тоже файл `report_<TASK>.md`, и он ошибочно засчитывался успехом. **Кейс projecta T6-DEPLOY (2026-06-27):** заблокированный каналом деплой (буфер AnyDesk не пробрасывался) попал в лог как `SUCCESS: report готов` + `✅`, после чего queue-сторож `queue_deploy_after_t7.sh` по `[ -f report_T6-DEPLOY.md ]` решил «deploy уже сделан» и **не перезапустил** деплой по уже разблокированному (RustDesk) каналу — день простоя.

**Теперь** появление отчёта = только сигнал ФИНИША; supervisor читает в нём строку `STATUS: SUCCESS|FAIL|BLOCKED|PARTIAL` (`STATUS_RE` в шаблоне) и:
- `SUCCESS` → `✅` + `exit 0`;
- `FAIL|BLOCKED|PARTIAL` → `⚠️` + `exit 2` (отчёт есть, но НЕ успех);
- нет строки STATUS → `⚠️` + `exit 3` (достоверность не подтверждена — заставляет автора таска добавить маркер).

Поэтому таск-файл **обязан** в самом конце отчёта писать строку `STATUS: ...` (см. «Формат таск-файла»). Для старых тасков оставлена обратная совместимость: `LEGACY_SUCCESS_RE='МАРКЕР УСПЕХА'` трактуется как `SUCCESS`. Если таск пишет отчёт под другим именем — поправь `REPORT` в настройках.

> 🔴 **Идемпотентность очереди — по УСПЕХУ, не по существованию отчёта.** Queue/«уже сделано»-проверки **никогда** не должны опираться на `[ -f report_<TASK>.md ]` — провальный отчёт тоже существует. Опирайся на sentinel-файл успеха (напр. `reports/ALL_DONE_<WAVE>`, который пишется ТОЛЬКО при `STATUS: SUCCESS`) либо на саму `STATUS:`-строку. Иначе после провала волна «самозасчитается» сделанной и не перезапустится (тот же кейс projecta).

**Кейс projectb T-TASKA-COST-TEST (2026-06-01).** Агент 4 раза не доходил до результата: первые 3 — падал на `vnc_admin.sh up` (вложенный `runuser` от agentuser, см. отдельную заметку), 4-й — **завис на API-turn**: PID жив 33 мин, jsonl не рос ни байта, соединения только к API (не к стеку). Watchdog это не ловил (output.log=0 = «норма» для `-p`). Поставлен supervisor со stall-детектом по jsonl + auto-respawn + переподъём CDP-стека → агент пошёл под автоматическим надзором без участия человека в петле.

#### 9.8ter 🔴 Supervisor для ОРКЕСТРАТОРА (а не одиночного агента): stall-сигнал = НОВЕЙШИЙ jsonl ВСЕЙ волны

> Шаблон `single_agent_supervisor.template.sh` следит за jsonl **одной** сессии. Это верно для ОДИНОЧНОГО `-p`-агента
> (он — единственное, что должно «дышать»). Но если supervisor стережёт **ОРКЕСТРАТОР** (который сам спавнит саб-агентов
> через `runner.sh`) — следить за jsonl **самого оркестратора НЕЛЬЗЯ**: оркестратор **легитимно молчит**, пока ждёт долгий
> саб-агент (его собственный jsonl не растёт по 10-20 мин), а supervisor читает это как «завис на API-turn» и **зря убивает
> и перезапускает оркестратор**.

**Кейс projectd DELIVERY (2026-06-04).** Supervisor оркестратора с `STALL_LIMIT=600`, следящий за jsonl оркестратора.
Оркестратор заспавнил D1-DIMS (долгий таск ~25 мин), сам ушёл в ожидание `.done` → его jsonl затих на 644с → supervisor
счёл столлом и сделал `kill+respawn` оркестратора, **хотя D1-DIMS в этот момент активно работал** (его jsonl рос, 783 КБ).
Не катастрофа (RE-GREP guard не дал перезапустить D1 повторно), но лишний churn и риск упереться в `MAX_RESPAWN`.

**Правило.** Для supervisor'а оркестратора stall-сигнал = **возраст НОВЕЙШЕГО jsonl во ВСЁМ каталоге проекта**
(`-work-<проект>/`), а НЕ конкретной сессии. Пока растёт хоть один jsonl (оркестратора ИЛИ любого саб-агента) — волна жива.
Столл = молчат ВСЕ. И порог выше (15 мин), т.к. оркестратор по своей природе много ждёт.

```bash
# ❌ НЕ для оркестратора (ловит «молчание» оркестратора во время работы саб-агента):
J=$(find "$JSONL_DIR" -name '*.jsonl' -newermt "@$LAUNCH_TS" | xargs -r ls -t | head -1)   # только эта сессия

# ✅ Для оркестратора — новейший jsonl ВО ВСЁМ каталоге (оркестратор + саб-агенты):
NEWEST=$(ls -t "$JSONL_DIR"/*.jsonl 2>/dev/null | head -1)
AGE=$(( $(date +%s) - $(stat -c %Y "$NEWEST") ))
[ "$AGE" -ge "$STALL_LIMIT" ] && kill_orchestrator && respawn   # STALL_LIMIT=900 (15 мин), не 600
```

Готовый рабочий supervisor оркестратора — `/work/projectc/orch/orchestrator_supervisor.sh` (projectd):
определяет PID оркестратора как **потомка bash'а pane'а tmux** (а не `pkill -f claude` — иначе убьёт саб-агентов и чужие
сессии), kill'ает grace `TERM→KILL` только его, поднимает через launcher, выходит по `reports/ALL_DONE_*`.
Доп. остаток: **столл самого саб-агента** (его jsonl — новейший, но затих) этот сигнал тоже поймает, но действие
(respawn оркестратора) саб-агента не лечит — если важно, добавь ветку «новейший jsonl принадлежит живому runner-pid →
kill этого саб-агента, runner сам сделает retry».

🔴 **`handle_rate_limit` — во ВСЕХ ветках respawn (tmux-dead / claude-dead / STALL / no-jsonl), НЕ только в STALL** (как §9.3bis для одиночного агента). Кейс fb14 2026-07-06: клонированные `orchestrator_supervisor_fb*.sh` звали `handle_rate_limit` ТОЛЬКО в ветке STALL. Для интерактивного claude 5ч/session-лимит обычно и проявляется как STALL (REPL жив, но встал — jsonl не растёт), поэтому чаще срабатывало. НО если лимит проявится как СМЕРТЬ claude/tmux (ветки 2/3), они делают `respawn` без RL-проверки → жгут `respawn_count` (при `MAX_RESPAWN` относительно лимита в часы — исчерпают и умрут с `❌ respawn исчерпан` ещё до сброса квоты. То же, что кейс PROJECTA §9.3bis, но на уровне оркестратор-супервизора). Правило: в КАЖДОЙ ветке смерти/столла — `if handle_rate_limit; then continue; fi` ПЕРЕД `respawn_count++`. `handle_rate_limit` там безопасен: `rl_marker` читает свежий jsonl (age < RL_WAIT+600) + pane — при смерти claude pane пуст, но маркер лимита остаётся в jsonl; `kill_orch` на мёртвом PID = no-op, дальше `launch_orch` после сброса. При клонировании супервизора под новую волну — свери, что RL-ветка есть во ВСЕХ ветках respawn (у оркестратор-супервизора их три: tmux-dead / claude-dead / STALL; у одиночного §9.8bis — четыре, +no-jsonl).

#### 9.10 Уроки projectd 2026-05-26 (post-mortem)

Кейс: projectd projectc orchestrator, 6 task-волн (T01-T06) + 2 follow-up (T07-T08). 4 разные проблемы за одну ночь, ни одна не была покрыта тогда-актуальными шаблонами. Все 4 теперь добавлены ниже + в `orchestrator_watchdog.template.sh` и в новый `tasks_runner.template.sh`.

##### 9.10.1 Sub-agent умер от API timeout — никто не respawn

**Что было:** В 07:21 Anthropic API получил серию timeouts. T05 + T06 sub-agents (запущенные через `setsid claude -p`) синхронно умерли с `Request timed out` в log'е. Main orchestrator продолжал крутиться в `Monitor` (висел на polling). Watchdog видел смерть sub-agent'ов в логе (PIDs ушли из `alive`), но respawn-логики у него не было — только TG-пинг.

**Прошло 25 минут пустого ожидания**, потом сам tmux упал (вероятно OOM/cascade).

**Фикс №1 — sub-agent wrapper с retry:** все sub-agents запускаются НЕ напрямую через `setsid claude -p`, а через wrapper-скрипт `tasks_runner.sh` (см. шаблон `/work/settings/claude/tasks_runner.template.sh`):
```bash
# Вместо:
setsid runuser -u agentuser -- claude -p < tasks/T05.md > logs/T05.log 2>&1 &

# Использовать:
setsid /work/<project>/tasks/runner.sh T05 &
```
Wrapper делает `for i in 1..3: claude -p < task && break; sleep $((i*60))`. После 3 fail-ов — пишет `reports/T05.failed` + TG-пинг.

**Фикс №2 — sentinel-файлы:** sub-agent в самом конце своей работы пишет `reports/Txx.done` (атомарно через `mv tmp/Txx.done.tmp reports/Txx.done`). Watchdog и orchestrator проверяют **файл**, не PID — потому что sub-agent может уже завершиться к моменту проверки PID. Также `done`-файл переживает любой crash sub-agent'а.

**Фикс №3 — watchdog respawn-блок:** добавлен шаг 5b в `orchestrator_watchdog.template.sh` — для каждого `tasks/Txx.md` без отметки в `progress.md` и без `reports/Txx.done`: если `pid_file` указывает на мёртвый PID **и** log содержит `Request timed out` → respawn через wrapper (с retry-счётчиком в state-dir, лимит 3).

##### 9.10.2 Повторный запуск уже-готового таска

**Что было:** В 06:39 orchestrator запустил T04 sub-agent во **второй** раз (PID 23676), несмотря на то что:
- `progress.md` уже имел `[x] T04 БД-схема ... 2026-05-26 02:18`
- `git log` имел `3e36da0 T04: DB schema + RLS`
- `reports/T04_report.md` весил 9.5KB
- `chat`-pane ранее показывал `✔ T04`

Причина: внутренний TODO-tree orchestrator-а имел `T04 ◼ in_progress` (drift между in-memory TODO и filesystem). §9.2 пункт 3 говорил «синхронизируй ОДНО с ДРУГИМ», но как **правило**, не как **enforce**.

**Фикс — жёсткий guard в resume prompt:**
```markdown
## RE-GREP GUARD (mandatory before any sub-agent launch)

Перед `setsid ... runner.sh <TASK>`:
1. `grep -E "^- \[x\].*${TASK}\b" chat/orchestrator_progress.md` → если match: SKIP, write «[skip] T05 already in progress.md»
2. `test -f reports/${TASK}.done` → если match: mark `[x]` in progress.md if not yet, SKIP
3. `test -f /tmp/orv_${TASK}.pid && kill -0 $(cat ...)` → если живой PID: SKIP («already running»)
4. Только если все 3 чека прошли — spawn.

ЕСЛИ ТЫ ВИДИШЬ В СВОЁМ TODO-tree «T04 in_progress», НО `progress.md` имеет `[x] T04` — это drift. **Доверяй файлу, не памяти.** Обнови TODO, не запускай повторно.
```

##### 9.10.4 Main orchestrator упал — A-cron watchdog ждал */15

**Что было:** Когда tmux server упал в ~07:46, A-watchdog (cron */15) должен был тикнуть в 08:00, обнаружить смерть и relaunch. Но cron-демон в WSL **был остановлен** (после ребута WSL `service cron start` не отрабатывает автоматически). **Получилось**: оба watchdog-а мертвы, orchestrator мёртв, юзер обнаружил это сам утром.

**Фикс №1 — cron-readiness check в launcher:**
```bash

if ! pgrep cron > /dev/null; then

```

**Фикс №2 — B-watchdog под root, не agentuser:**
B-loop должен запускаться от **root** (`tmux new-session -d -s orch_watchdog_loop ...` без `runuser`), чтобы при смерти основного tmux-сокета agentuser (`/tmp/tmux-1000/default`) B-loop пережил это — у root свой сокет (`/tmp/tmux-0/default`). Если проект надо охранять очень надёжно — добавить cron-задачу `* * * * *` (каждую минуту), которая ТОЛЬКО проверяет «жив ли B-watchdog tmux» и relaunch'ит его. Так A + B + supervisor — три уровня страховки.

#### 9.11 🆕 Дедлайн-стоппер — жёсткий стоп сборки по таймеру (кейс projecte 2026-06-10)

**Когда нужен:** юзер просит «пусть работает, но через N часов прекратил». Просто
дописать дедлайн в промпт оркестратора НЕДОСТАТОЧНО: (а) оркестратор может зависнуть
и не посмотреть на часы; (б) даже если он выйдет сам — **watchdog'и его воскресят**
(они для этого и существуют). Нужен внешний механизм, который перебарывает всю
самовосстанавливающуюся машинерию §9.8–9.10.

**Шаблон:** `/work/settings/claude/deadline_stopper.template.sh`. Боевой пример:
`/work/projecte/chat/deadline_stopper.sh` (стоп через 5ч, этап C).

**Архитектура — три слоя (каждый сам по себе недостаточен):**

1. **Мягкий слой — дедлайн в resume-промпте оркестратора.** Секция «⏰ ДЕДЛАЙН
   (ЖЁСТКИЙ)»: точное время стопа; за ~25 мин до него — прекратить спавны, дождаться
   текущего саб-агента, обновить progress.md, **закоммитить**, финальный TG.
   Это даёт *чистый* финиш (зафиксированный прогресс), но не гарантирует стоп.
2. **Жёсткий слой — стоппер-скрипт от ROOT в своём tmux** (`<TAG>_deadline`),
   запускается вместе с launcher'ом. Цикл `while date+%s < DEADLINE_TS; sleep 60` —
   🔴 НЕ один длинный `sleep`: гибернация/idle WSL замораживает sleep, абсолютный
   timestamp — переживает. В дедлайн, строго в этом порядке:
   - сентинел `chat/DEADLINE_STOP` (дата-время внутри);
   - **сначала обезглавить воскрешателей**: cron-A (`grep -v orchestrator_watchdog | crontab -`),
     B-loop tmux, ram_guard tmux, state-dir;
   - грейс-килл саб-агентов **по группам процессов** из pid-файлов своего тэга
     (`/tmp/<TAG>_*.pid`; runner стартует `setsid` → PID=PGID → `kill -TERM -- -PID`),
     30с ожидания, добив `kill -9 -- -PID`;
   - убить tmux оркестратора (на сокете agentuser: `runuser -u agentuser -- tmux kill-session`);
   - TG-пинг с честным статусом (сколько тасков `[x]`).
   Самоснятие: если до дедлайна в progress.md не осталось `[ ]`/`[~]` — выйти без действий.
3. **Сентинел-проверки во всех точках перезапуска** — иначе любой выживший/будущий
   тик воскресит сборку:
   - `launch_orchestrator.sh`, первая строка логики: `[ -f chat/DEADLINE_STOP ] && exit 0`;
   - `orchestrator_watchdog.sh`, шаг «-1» до всех остальных: сентинел есть →
     самоликвидация (снять себя из cron, убить B-loop, `rm -rf STATE_DIR`, exit).
     В шаблон watchdog'а добавлено (2026-06-10).

**Грабли, собранные в кейсе projecte (все учтены в шаблонах):**

- **B-loop срабатывает мгновенно после установки**, ДО того как оркестратор успел
  стартовать первую волну → watchdog шага 4b заспавнил ВСЕ 4 таска разом, сломав
  порядок волн и RAM-лимит (≤2). Фикс в шаблоне watchdog: `logs/<ID>.log` НЕ
  существует = таск ещё ни разу не стартовал = это работа ОРКЕСТРАТОРА, watchdog
  не лезет (`[ -f "$TASK_LOG" ] || continue`). Преждевременно заспавненных убивать
  по группе: `kill -9 -- -<PGID>` (PGID = PID из pid-файла), удалить их pid-файлы
  и `respawn_*`-счётчики из state-dir.
- **Generic-имена state ловят коллизии между проектами:** `STATE_DIR=/tmp/orch_watchdog_state`
  и tmux `orch_watchdog_loop` из шаблона надо ПЕРЕИМЕНОВАТЬ в `<TAG>_*`
  (`/tmp/insc_watchdog_state`, `insc_watchdog_loop`) — на машине одновременно жил
  второй оркестратор (projectd), чужой state-dir = ложные счётчики respawn.
- **Kill только своего:** все убийства — по явным `<TAG>_*` pid-файлам и
  tmux-именам с exact-match (`-t "=имя"`). Никогда `pkill claude` — соседние
  оркестраторы (orv_* и т.п.) трогать нельзя.
- **TOTAL_TASKS в watchdog** при добавлении новой волны к уже завершённым этапам =
  старые `[x]` + новые таски (иначе формула done/total и финал-детект врут).
- Перед запуском новой волны: `rm -f /tmp/<TAG>_*.pid chat/DEADLINE_STOP`,
  `rm -rf /tmp/<TAG>_watchdog_state` — мусор прошлой волны = ложные SKIP/respawn.

```markdown
🔴 **ПОРЯДОК ЗАВЕРШЕНИЯ ЖЁСТКИЙ (правка 12.08.2026, GOTCHAS #16): сначала git, потом STATUS.**

```
1. git add по своей зоне → git commit → git push
2. вписать РЕАЛЬНЫЙ хеш в отчёт (плейсхолдер = отчёт не принят)

```
Причина не стилистическая. Супервизор снимает агента **в тот же миг**, когда видит валидную строку
`STATUS:` — это его штатное поведение (`finish_on_report` → `kill_agent`). Значит всё, что агент
планировал сделать ПОСЛЕ статуса, не будет сделано никогда. Пять задач подряд 11-12.08 закрылись
без своего коммита именно поэтому: требование «коммит — часть работы» стояло в шапке, а порядок
действий делал его недостижимым. Работу за них коммитили следующие задачи и человек.

С 12.08 супервизор дополнительно проверяет это сам (`COMMIT_GATE`): увидев STATUS при грязном
дереве или плейсхолдере вместо хеша, он один раз просит агента довести работу до git и ждёт
`COMMIT_GRACE` секунд, и только потом закрывает — уже с громким предупреждением в лог и в TG.
Гейт — страховка, а не замена порядку: правильный порядок дешевле.

- Записать `chat/report_<TASK>.md`. ПОСЛЕДНЯЯ строка отчёта — статус, ровно один из:
  `STATUS: SUCCESS` | `STATUS: FAIL` | `STATUS: BLOCKED` | `STATUS: PARTIAL`.
  По ней supervisor отличает реальный успех от честно-зафиксированного провала (см. §9.8). Без неё финал = `⚠️` «достоверность не подтверждена».

  🔴 `BLOCKED` — только РЕАЛЬНАЯ внешняя преграда (проверенная), НЕ «страшно / живая система / нужно на месте / сомнение». Ложный стоп так же недостоверен, как ложный SUCCESS — см. §6.1.
```

## 10. Уведомления и вопросы агента → юзеру через Telegram

Print-режим (`claude -p`) не интерактивен — агент **не может** ждать ответа юзера inline. Единственный канал из таск-агента до юзера — Telegram. **В каждом таск-файле** должен быть явно указан bot path и сценарии когда пинговать.

### 🔴🔴 10.0 `-p`-саб-агент НЕ ДОЛЖЕН «уступать ход» / ждать переинвока — иначе бесконечный respawn-цикл

**Правило:** в режиме `claude -p` **конец хода = выход процесса**. Нет «фоновой задачи, которая меня переподнимет», нет ScheduleWakeup-переинвока, нет «я подожду уведомления и продолжу» — всё это фичи ИНТЕРАКТИВНОЙ сессии (main-loop), которых в `-p` НЕТ. Как только модель заканчивает ответ (в т.ч. фразой «I'll wait / I'll yield until … re-invokes me / дождусь уведомления»), `claude -p` завершается. Супервизор видит «SUB_PID DEAD без отчёта» → respawn → новый агент так же уступает → **бесконечный цикл ~N минут, без прогресса, до исчерпания MAX_RESPAWN → ложный BLOCKED всей волны.**

🔴 **Кейс T-STOREFRONT-BACKUP (projectb, 2026-07-10):** агенты бэкапа каждые ~10 мин умирали «DEAD без отчёта» (НЕ OOM, НЕ stall-kill, НЕ песочница — RAM свободна, dmesg чист). В jsonl концовки: «Backup launch still in its backoff window. **I'll wait for the background job to complete and notify me**», «Back-off still in progress… **I'll yield until the 4-minute back-off completes and re-invokes me**». Агент запускал бэкап фоново/детачнуто и «уступал ход, чтобы его переподняли», — в `-p` это = выход. 4 respawn'а впустую.

**Как правильно (обязательно для длинных операций в `-p`):**
- **Всё ожидание — блокирующим циклом В ТОМ ЖЕ ХОДЕ.** Запустил долгую работу (server-side `nohup`/detached, tar/dump/scp, сборка, прогон) → **тут же поллишь её завершение синхронным bash-циклом** до появления sentinel/готового файла, и только потом идёшь дальше и пишешь отчёт. Пример:
  ```bash
  # запустить детачнуто на сервере (переживёт обрыв SSH)
  ssh ... 'nohup bash /path/run_backup.sh >/path/backup.log 2>&1 & echo $! > /path/backup.pid'
  # ПОЛЛИТЬ В ТОМ ЖЕ ХОДЕ (blocking), НЕ «уступать»:
  for i in $(seq 1 120); do
    ssh ... 'test -f /path/DONE && echo READY || echo WAIT'   # sentinel-файл, пишется в конце run_backup.sh
    [ "$(...)" = READY ] && break
    sleep 30
  done
  ```
  Каждый такой `sleep`/`ssh`/`curl` — с **`dangerouslyDisableSandbox: true`** (песочница режет долгие/ожидающие процессы сигналом 16; см. §9a).
- **НЕЛЬЗЯ** в `-p`: `ScheduleWakeup`, `run_in_background` + «дождусь нотификации», «yield/уступлю ход и продолжу по завершении фона». Эти паттерны молча убивают агента.
- **Один foreground-`Bash` ≤ ~10 мин** (потолок исполнения). Если операция дольше — детач на сервере + короткие поллы (как выше), а не один 30-минутный форграунд.
- Если работа реально не влезает в один ход даже поллингом — это ПРОГРЕСС на диске (server-side job идёт) + агент опрашивает готовое; при respawn'е новый агент должен СНАЧАЛА проверить, не завершилась/не идёт ли уже фоновая работа (идемпотентность), и не перезапускать её с нуля.

**Это должно быть в каждом таск-файле** (секция «Правила»), где агент делает длинные операции. Супервизор лечит транзиентные падения (API-blip), но НЕ лечит «агент сам уступает ход» — это правится ТОЛЬКО в промпте/таск-файле.

### 🔴 10.0b Отчёт писать ОДИН раз В КОНЦЕ (не скелет заранее) — иначе супервизор прервёт на полпути

Супервизор ловит ФИНИШ по **факту существования файла отчёта** (`if [ -f $REPORT ]; then finish_on_report`), а успех — по строке `STATUS:` внутри. Если агент создаёт отчёт-**скелет заранее** (с плейсхолдерами и без `STATUS:`), то на ПЕРВОМ же опросе супервизор увидит файл без `STATUS:` → выведет `AMBIGUOUS` (exit 3) и **прервёт очередь**, хотя агент ещё работает. И при перезапуске старый отчёт без `STATUS:` вызовет мгновенный `AMBIGUOUS` снова.

**Правило (в таск-файл + при перезапуске):**
- Агент пишет `report_<TASK>.md` **ОДИН раз, в самом конце, полностью заполненным**, с последней строкой `STATUS: SUCCESS|FAIL|BLOCKED|PARTIAL`. Никаких ранних скелетов/плейсхолдеров в файле отчёта.
- 🔴 **Перед перезапуском таска — заархивировать старый отчёт** (`mv report_<TASK>.md report_<TASK>_runN.md`) и вычистить stale-PID, иначе супервизор мгновенно финиширует на старом файле (idempotent-капкан, ср. SEQUENTIAL_ORCHESTRATORS.md).

🔴 **Кейс T-REG-RU-EMAIL-ONLY (projectb, 2026-07-12):** агент собрал и закоммитил аддон, но написал отчёт-скелет с `<!-- STATUS -->` до staging-теста → супервизор поймал файл без `STATUS:`, вывел AMBIGUOUS и увёл очередь дальше, не дав дойти до деплоя/тестов. Параллельно T-HAIRMEDICA самозаблокировался (BLOCKED) из-за УСТАРЕВШЕЙ ссылки в гейте на `report_T-NKGROUP-STOREFRONT-APPLY.md` (тот BLOCKED), хотя нкгруп сделан отдельным таском RECREATE (SUCCESS) — при замене таска новым **обновляй gate-ссылки во всех зависящих таск-файлах**.

### 10.0c Гейт грязного дерева: SUCCESS не засчитывается, если работа не закоммичена

Вердикт задачи всегда ставился по строке `STATUS:` в отчёте, а состояние рабочего дерева не
проверялось ни на одном шаге. Из-за этого задача могла закрыться успехом, оставив правку висеть
неучтённой рядом с деревом, где уже работает следующий агент: одна `git checkout` — и смена
потеряна.

ВАЖНО, реальный случай (очередь «Товары из Китая», ночь 22.08.2026): за одну смену так закрылись
три задачи подряд. T281 написала себе `STATUS: SUCCESS`, а её правка на 73 строки висела
незакоммиченной; T282 оставила приёмку на 216 строк; T254 забыла скрипт разового прохода. Всё
нашлось только при ручном разборе наутро.

Теперь `claude_orchestrator.template.sh` перед тем, как записать SUCCESS в журнал, зовёт
`dirty_tree_report()`: если в рабочем дереве есть незакоммиченное, вердикт понижается до `PARTIAL`,
в лог идёт строка `DIRTY-TREE <таск>: ...` с перечнем файлов, и уходит уведомление. Отчёт агента
при этом НЕ переписывается — гейт правит только журнал очереди.

Настройки:

| переменная | по умолчанию | зачем |
|---|---|---|
| `GIT_DIRTY_GATE` | `1` | `0` выключает гейт для проекта (ставить в его `_run_orch.sh`) |
| `GIT_DIRTY_DIRS` | `$PROJECT_DIR/app $PROJECT_DIR` | где искать репозитории; корень определяется через `git rev-parse --show-toplevel`, дубли схлопываются |
| `GIT_DIRTY_IGNORE_RE` | снимки, логи, отчёты, сборочный мусор | артефакты прогонов в репозитории не держим, и гейт на них молчит — иначе он срабатывал бы вхолостую после каждого прогона |

Что это значит для агента: коммит — часть работы, а не «потом». Если правка сознательно не
коммитится, это надо назвать в отчёте и закрыться `PARTIAL`, а не `SUCCESS`.

После `python3 /work/tg/bot.py send ...` агент **выходит** (print-mode). Если юзеру нужно ответить — он запускает **новый** таск (например `task_retry_<имя>.md`) с обновлённой инструкцией. Это нормально.

Если хочется чтобы агент дождался ответа — нужен tmux-оркестратор (см. §9), но это overkill для одиночного таска.

### 10.5 Лимиты и форматирование

- Telegram API: max ~4096 символов в сообщении. Длинные репорты — ссылкой на файл (`Отчёт: /work/shop/chat/report_<имя>.md`), не текстом.
- **🆕 Markdown больше не блокирует доставку.** `bot.py` шлёт сначала с `parse_mode=Markdown`, а если Telegram возвращает 400 «can't parse entities» — автоматически делает retry **без** parse_mode (с 2026-05-24). То есть финальные TAIL отчётов агентов / стрингс с `**bold**` / `` `code` `` / `[link]` / `_italic_` теперь **всё равно доставляются** как plain text. Не нужно вручную экранировать в обычных пингах.
- ⚠️ Тем не менее, если хочется чтобы Markdown **сработал** (отрисовался жирным/курсивом) — следить за балансом метасимволов: парный `**bold**`, корректное закрытие `` ` `` / `[...](...)`. При первой 400-ошибке plain-text fallback гарантирует доставку, но без форматирования.
- **🆕 Sendphoto + caption:** PNG/JPG до 10 MB, caption до 1024 символов. Если caption длинее — обрезается. Telegram пережимает фото в JPEG — для скринов с мелким текстом лучше использовать обрезку (`page.screenshot({clip: {...}})`) вместо `fullPage: true`, либо `convert -resize 'x2000>'`.
- НЕ слать пароли / токены / приватные URL в TG (они кэшируются на сервере Telegram).
- **UTF-8:** watchdog'и и bash-скрипты под `env -i` должны экспортировать `LC_ALL=C.utf8 LANG=C.utf8` перед вызовом `bot.py`, иначе Python печатает текст как ASCII и Telegram отдаёт 400 «text must be encoded in UTF-8» (исправлено в шаблоне watchdog'а на 2026-05-24).

### 10.6 Получить ответ юзера (для оркестратора)

Юзер пишет боту → запись попадает в `/work/tg/inbox.jsonl`. Структура:
```json
{"ts":"2026-05-11T20:16:50.692948","message_id":3938,"chat_id":YOUR_TELEGRAM_CHAT_ID,"from_id":YOUR_TELEGRAM_CHAT_ID,"from_username":"user","text":"...","read":false}
```

Чтобы оркестратор увидел ответ — polling:
```bash
# Последние непрочитанные от нужного юзера
tail -50 /work/tg/inbox.jsonl | python3 -c "

for line in sys.stdin:
    m = json.loads(line)

```

Маркируй отвеченные пометкой `YOUR_KEY` (короткий идентификатор таска в начале), чтобы не путать с другими сообщениями юзера.

### 10.8 🆕 Кейс 2026-05-24 — Markdown fallback + sendphoto + UTF-8

**Проблема 1 (Markdown):** Watchdog'и при финальном пинге `ℹ️ <TASK> завершился без success-маркера. Хвост: <TAIL>` падали с `API error sendMessage: 400 ... can't parse entities`. **Проблема 2 (UTF-8):** При запуске watchdog'а через `env -i` (чистое окружение) Python печатал text bytes как ASCII → Telegram 400 «text must be encoded in UTF-8».

**Новая фича — sendphoto:** добавлена CLI команда `python3 /work/tg/bot.py sendphoto <chat_id> <path> [caption]`. ## 11. Trust-list для папок (Quick safety check)

Когда `claude` запускается с CWD, которой пользователь ещё не доверял, CLI показывает блокирующий prompt:
```
Do you trust the files in this folder?
> 1. Yes, proceed
  2. No, exit
```
**В этот момент любая команда / paste-buffer уходит В МЕНЮ trust prompt'а и теряется.** Поэтому критично проверять состояние trust ДО запуска и/или принимать prompt в launcher'е.

### 11.1 Где хранится trust-state

`~/.claude.json` пользователя, **который запускает claude** (НЕ root, если работаем от agentuser). Формат:
```json
{
  "projects": {
    "/work/shop": { "allowedTools": [], "history": [...] },
    "/work/projectb": { ... }
  }
}
```
Ключ `"/work/<dir>"` присутствует ↔ папка trusted для этого юзера. Файл `chmod 600`, читать только под нужным юзером (или root).

### 11.2 Pre-flight check (рекомендуется ДО launcher'а)

Перед запуском оркестратора / sub-агента в новой папке:
```bash
runuser -u agentuser -- grep -c '"/work/<dir>"' /home/agentuser/.claude.json
# 1 = trusted, 0 = НЕ trusted (будет prompt при первом claude в этой папке)
```

Если `0` — варианты:
1. **Принять заранее интерактивно** — `runuser -u agentuser -- bash -c "cd /work/<dir> && claude"`, нажать `1 Enter` или просто `Enter` (default Yes), `Ctrl-C` чтобы выйти. После этого `~/.claude.json` пополнится.
2. **Положиться на trust-Enter в launcher'е** (см. §11.3).

### 11.3 Trust-Enter в orchestrator launcher (tmux)

Если launcher запускает claude в новой папке через `tmux send-keys` (см. §9.1) — обязательно после `send-keys "claude ..." Enter` подождать ~5 сек и послать дополнительный `Enter` для принятия default «Yes» опции trust prompt'а:

```bash
runuser -u agentuser -- tmux send-keys -t $SESSION "claude --dangerously-skip-permissions" Enter
sleep 5
runuser -u agentuser -- tmux send-keys -t $SESSION Enter   # принять trust (no-op если уже trusted)
sleep 20  # claude инициализируется
# теперь можно paste-buffer и далее
```

Этот Enter:
- На свежей папке: принимает trust prompt (default = Yes = опция 1).
- На уже-trusted: безвредный no-op (главный prompt не съест пустой Enter без текста перед ним).

### 11.4 Sanity-check после trust-Enter (must-have)

После всех Enter'ов и пасты — обязательно проверить, что не висим в trust-меню:
```bash
sleep 3
if runuser -u agentuser -- tmux capture-pane -t $SESSION -p | grep -q "Quick safety check\|Yes, I trust\|Do you trust"; then
  echo "⚠️ FATAL: trust-prompt не принят, паста ушла в меню. Прибей session и перезапусти."
  exit 1
fi
```
Без этого может быть тихий fail: launcher вернул 0, tmux жив, но claude висит в trust-меню → sub-агенты никогда не запустятся.

### 11.5 Print-mode (`claude -p`) и trust

Поведение `claude -p` на untrusted папке **не задокументировано в CLI**. Эмпирически:
- Trusted папка → работает нормально.
- Untrusted папка → может молча выйти / упасть / зависнуть. Не было случая успешной автоматической работы.

**Правило для launcher'а §4** (`setsid runuser ... claude -p ...`): обязательно делать pre-flight check (§11.2). Если папка не trusted — сначала принять интерактивно (§11.2 п.1), потом запускать `-p`-агента.

### 11.6 Кейс 2026-05-18 (shop orchestrator setup)

При планировании запуска shop-оркестратора (от root, под agentuser) pre-flight check `/home/agentuser/.claude.json` показал что `/work/shop` уже trusted (был принят ранее). trust-Enter в launcher оставили как no-op-страховку — sanity-check на trust-prompt после паста подтвердил что меню не висит. Запуск прошёл без вмешательства.

Если бы папка была untrusted, и launcher не сделал бы trust-Enter+sanity — паста промпта ушла бы в меню, claude бы висел в Quick safety check, watchdog рапортовал бы «alive (есть claude PID)» но реальной работы не было бы. Pre-flight check спасает от этого молчаливого fail'а.

## 12. Очередь оркестраторов — запуск ВТОРОГО после финала ПЕРВОГО

> 📄 **Готовые шаблоны (оба направления цепочки) + дока — `/work/settings/`:**
> - `SEQUENTIAL_ORCHESTRATORS.md` — описание обоих паттернов с реальными кейсами (PROJECTA ↔ projectd, 2026-06-30).
> - `queue_wave_after_orchestrator.template.sh` — **Паттерн 1: волна B ПОСЛЕ оркестратора A** (сторож ждёт смерти supervisor-сессий A → гонит B).
> - `queue_wave_then_resume_orchestrator.template.sh` — **Паттерн 2: оркестратор A ПОСЛЕ волны B** (прогнать B → снять A с паузы / resume).
> - `wave_supervisor.template.sh` + `wave_launcher.template.sh` — RL-aware супервизор (5ч/session-лимит ждёт циклом, §9.3bis) + лончер, env-параметризованы; их и зовут очереди.
> - Старый одиночный шаблон «B после A»: `queue_next_orchestrator.template.sh`.
> Боевые копии: `/work/shop/chat/wave_projecta/` (queue_after_projecta.sh, queue_projectd_then_resume_projecta.sh) и `/work/projectc/orch/scripts/queue_after_projectb.sh` (projectb, 2026-06-12).

**Когда нужен:** юзер хочет «волна B стартует, когда волна A закончится», а параллелить нельзя (§8.7 синглтоны / §8.9 RAM). Дописать «подожди A» в промпт оркестратора B — НЕ работает: B пришлось бы уже запустить (claude в tmux жрёт RAM и подвержен тем же API-ямам, пока «ждёт»), а оркестратор A — чужой/уже бежит, его промпт не поправить. Решение — **внешний сторож-скрипт от root в своём tmux** (`<TAG_B>_qwait`): дешёвый bash, наблюдает финал A, затем стартует B.

### 12.1 Сигнал «первый закончился» — что брать и что НЕ брать

| Сигнал | Годится? |
|---|---|
| **Смерть tmux-сессии очереди/оркестратора A** (`! tmux has-session -t =NAME`) | ✅ основной: сессия умирает вместе с pane-командой (queue-runner-скрипт или claude+`/exit`) |
| progress.md волны A «все [x]» | ❌ A мог упасть, не дописав; либо формат чужой |
| pid-файлы A | ❌ бывают stale И отсутствуют при живом процессе (§9.10.2, Y6-кейс) |
| `reports/ALL_DONE_*` волны A | ⚠️ ок как ДОПОЛНЕНИЕ, если A гарантированно его пишет; но при крахе A файла не будет никогда — сторож зависнет. Смерть tmux-сессии покрывает и успех, и крах |

🔴 **Exact-match обязателен**: `tmux has-session -t =NAME` (с `=`). Без него — префиксный матч (§8.8): сторож в сессии `projectb2_queue_watch` «увидит сам себя» по `-t projectb2_queue` и будет ждать вечно. По той же причине свои имена сессий не должны быть префиксами друг друга.

### 12.2 Хвосты первой волны — ждать не только главную сессию

Очередь A могла породить **переживающие её сущности**: per-task supervisor'ы (`T-*_sup` — они РЕСПАВНЯТ агентов и после смерти очереди!) и setsid-detached `claude -p` агентов. Стартовать B поверх них = снова два оркестратора. Сторож после смерти главной сессии ждёт (с cap'ом ~4ч, чтобы зависший чужой supervisor не заблокировал B навсегда):
```bash
LEFT=$(tmux ls 2>/dev/null | grep -cE '^T-.*_sup:')          # чужие per-task sup'ы
AGENTS=$(pgrep -af 'claude' 2>/dev/null | grep -c projectb)  # чужие агенты по метке argv
```
Метка argv (`projectb`) работает потому, что `claude -p "<prompt>"` несёт весь промпт в командной строке. pgrep self-match (§8.5) не грозит: argv самого сторожа слова `claude` не содержит.

### 12.3 Порядок работ (чеклист)

```bash
# 0. ПОЛНОСТЬЮ подготовить волну B, НИЧЕГО из неё не запуская:
#    таск-файлы, progress.md, промпт оркестратора, launcher (§9.1), supervisor (§9.8ter).
#    Проверить: trust папки B (§11.2), нет старых sentinel'ов/pid-файлов B:
ls /tmp/<TAG_B>_T*.pid /work/<PROJECT_B>/reports/T*.done 2>/dev/null   # должно быть пусто/только старые волны
# 1. Скопировать шаблон, заполнить НАСТРОЙКИ (FIRST_SESSION, метки хвостов, RAM-гейт, пути B), chmod +x.
# 2. Взвести от root:
tmux new-session -d -s <TAG_B>_qwait "bash /work/<PROJECT_B>/orch/scripts/queue_after_<A>.sh"
# 3. Verify: в логе сторожа строка «armed», сессия видна:
sleep 3; tmux ls | grep qwait; tail -2 /work/<PROJECT_B>/orch/logs/<TAG_B>_queue_wait.log
# Отменить до старта B: tmux kill-session -t =<TAG_B>_qwait
```

Что делает сторож в момент срабатывания (порядок зашит в шаблоне):
1. смерть `=FIRST_SESSION` → 2. хвосты A затихли (cap) → 3. RAM-гейт (`MemAvailable ≥ 1.5Gi`) + `sleep 30` осесть → 4. **RE-check идемпотентности** (ALL_DONE B уже есть? supervisor B уже жив? → exit без дублей) → 5. старт `tmux <TAG_B>_sup` (supervisor сам поднимет оркестратор B через launcher) + RAM-сторож B → TG-пинг.

### 12.4 Грабли

- **Тики, не длинный sleep**: ожидание — циклом `sleep 120`, как в §9.11 (гибернация WSL замораживает один длинный sleep).
- **Сторож только НАБЛЮДАЕТ чужое**: никаких kill/pkill по сущностям волны A, даже «зависшим» — максимум cap + идти дальше. Гасить чужой supervisor решает юзер.
- **Supervisor B должен знать про RAM-паузы**: если у B есть ram_guard (SIGSTOP саб-агентов), stall-детект supervisor'а B обязан проверять state-файл паузы (`/tmp/<tag>_ram_paused`) и не считать SIGSTOP-тишину jsonl столлом — иначе kill+respawn здорового оркестратора.
- **Запускать сторож ДО ухода спать, проверять «armed» в логе**: молчаливый fail сторожа (опечатка в пути supervisor'а) = волна B не стартует никогда. Минимум — `bash -n` скрипта и tail лога после взвода.
- **TG-пинг при старте B** — юзер должен узнать, что эстафета передана (иначе утром непонятно, почему B бежит/не бежит).
- 🔴 **Ресурс/RAM-гейт ОБЯЗАН логировать КАЖДЫЙ тик, включая провал при `ok=0`; и не держать бесконечно после того, как сосед УЖЕ подтверждённо завершился.** Кейс fb14↔PROJECTA 2026-07-06: сторож корректно поймал финал PROJECTA (supervisor-сессия исчезла + хвосты затихли), но «устойчивый» RAM-гейт (`SUSTAIN×POLL`, порог 2.6Gi, no-chrome) в ветке `else` логировал только при `ok!=0` → при `ok=0` МОЛЧАЛ, и ~50 мин выглядел зависшим/мёртвым, хотя PROJECTA давно закончился (RAM после соседа болталась чуть ниже порога). Правила: (1) в гейте `log` на КАЖДОЙ итерации (и OK `n/SUSTAIN`, и fail — печатать `avail`/`chrome`), иначе «ждёт» неотличимо от «сдох»; (2) сигнал финала соседа (смерть supervisor-сессии + затихшие хвосты) — ПЕРВИЧНЫЙ; RAM-гейт ПОСЛЕ него — ЛЁГКАЯ страховка, не тугой многоминутный порог, который держит вечно на колебаниях `MemAvailable`; (3) не завышай порог/`SUSTAIN` — заниженная свободная RAM после соседа не даст гейту сойтись. Если сосед точно завершён и RAM свободна, а гейт «молчит» — это он, а не смерть: подними волну руками (`tmux new-session -d -s <B>_sup …`), сторож идемпотентно сам выйдет.
- 🔴 **Снимать/перезапускать сторож — по tmux-СЕССИИ (`tmux kill-session -t =<name>`), НЕ `pkill -f '<путь_скрипта>'`.** Кейс fb14 2026-07-06: `pkill -f 'queue_fb14_after_zkiosk'` / `for p in $(pgrep -f 'queue_fb14…')` **убил собственный shell** — argv моей же bash-команды содержит эту подстроку → pkill/pgrep self-match (флип-сайд §8.5, но здесь self-KILL) → команда умерла с `exit 128+16=144`, а перезапуск ПОСЛЕ pkill не выполнился. Гаси по имени сессии (exact `=`), а не по паттерну пути, который есть и в твоём argv.
- 🔴 **НЕ редактируй скрипт, который прямо сейчас крутится в detached-tmux (сторож/супервизор в `while sleep`-цикле).** bash читает скрипт по байтовому оффсету; правка файла сдвигает оффсеты → когда цикл выйдет из `sleep`, bash продолжит с середины строки НОВОГО файла → syntax error / мусорное поведение. Кейс fb14 2026-07-06: поправил список тасков в TG-строках уже запущенного `queue_fb14_*.sh`. Правильно: правь файл → `bash -n` → **ПЕРЕЗАПУСТИ начисто** (kill-session + `tmux new-session`); сторож идемпотентен (на старте чек `ALL_DONE`/supervisor-сессии → не задвоит волну).

Что делает в момент X, по порядку:
1. **RAM-гейт**: `available < MIN_RAM_MI` (по умолчанию 1500 Mi) → волна НЕ стартует. Лучше не начать,
   чем словить OOM посреди деплоя (урок 29.07, `RAM_GUARD.md`).
